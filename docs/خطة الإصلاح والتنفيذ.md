# خطة الإصلاح والتنفيذ لمنصة محلك

> **الإصدار:** 1.0 — يونيو 2026 · **النطاق:** إغلاق جميع المشاكل وتطبيق توصيات البحث · **المصدر:** باكلوغ موحّد من 70 مهمة مستخرَجة من (خطة التطوير + تدقيق الوضع الحالي + الدين الأمني + فجوات الجمهور) ومؤرَّضة في الكود الفعلي.
>
> **كيف تُقرأ:** المهام مرتّبة في **مراحل تحكمها التبعيات** لا مجرد الأولوية. كل مهمة لها معرّف ثابت (SEC/ADM/TRU/VIS/IA/UX/MOB/TD) يمكن تتبّعه. ابدأ من المرحلة 0 ولا تنتقل لمرحلة قبل تحقّق "تعريف الإنجاز" للسابقة في مساراتها الحرجة.

## المبادئ الحاكمة

1. **الأمان أساس يسبق كل شيء** — لا ميزة جديدة قبل إغلاق ثغرات قاعدة البيانات المكشوفة الآن.
2. **التبعيات تحكم الترتيب** — العرض يقود الطلب، فترتيب الشرائح: **البائع ← الأدمن ← المشتري ← السائق**.
3. **الثقة هي العملة** — COD، الإرجاع، التتبّع، المراجعات، قناة تواصل البائع.
4. **أكبر الفجوات المُدِرّة وظيفية لا تجميلية** — دفتر الديون والإشعار الموثوق وإشارات الثقة تسبق صقل الهوية الإبداعي.
5. **الخفّة وRTL وإمكانية الوصول إلزامية** — معيار عرضي على كل مهمة جديدة، لا مرحلة منفصلة.

## ⚠️ بند توفيق مهم: حالة الأمان الفعلية

جزء من بنود الأمان استُخرج من مذكّرة تدقيق سابقة، وقد جرى **التحقق الفعلي من الكود الآن** لتفادي إعادة إصلاح ما أُصلِح:

| الحالة | البنود | الدليل |
|---|---|---|
| 🔴 **مفتوح حرج (مؤكَّد)** | `SEC-02` قواعد قاعدة البيانات | لا `firestore.rules` ولا `storage.rules` ولا `firebase.json` في المستودع؛ العميل يكتب `role` مباشرةً عبر `setDoc` في `lib/auth-context.tsx` (215/253/348) — أي مستخدم يرفع نفسه `admin`. **قاعدة البيانات مكشوفة عبر Web SDK الآن.** |

#### SEC-02 — قواعد أمان Firestore وStorage (غائبة تمامًا) + منع كتابة role من العميل
- **المشكلة:** لا يوجد firestore.rules ولا storage.rules ولا firebase.json في المستودع (مؤكد بالفحص). العميل يكتب مباشرة إلى مجموعة users عبر setDoc في lib/auth-context.tsx (215/253/348)، فقاعدة البيانات مفتوحة بالكامل عبر Web SDK: أي مستخدم مُصادَق يقرأ/يكتب أي مستند ويرفع role:'admin' لنفسه — والدور هو أساس صلاحية الأدمن (orders.ts:448، session.ts getCurrentUser:70-74 يقرأ data.role). يمكن أيضًا التلاعب بالمخزون/الأسعار/الطلبات مباشرة متجاوزًا server actions.
- **الإصلاح:** إنشاء firestore.rules/storage.rules/firebase.json بقاعدة deny-all افتراضية: users يقرأ/يكتب صاحبه فقط مع منع تعديل حقل role من العميل (role يُضبط server-side عبر Admin SDK فقط، ويُفضّل custom claims للأدمن يُتحقَّق منها عبر verifySessionCookie)؛ orders/order_items/products/offers/reviews/notifications منع كتابة العميل كليًا (كل التعديلات عبر Admin SDK) وقراءة محدودة؛ Storage يقيّد product-images وصور الهوية على المالك بأنواع/أحجام محددة. نقل كل كتابة role إلى server action ومراجعة مسارات register/login/google. نشر عبر firebase deploy.

#### SEC-01 — طبقة تفويض موحّدة: requireAdmin/requireRole + middleware + layouts حارسة لكل المسارات الحساسة
- **المشكلة:** لا يوجد middleware.ts ولا app/seller/layout.tsx ولا app/driver/layout.tsx (مؤكد بالفحص الفعلي: كل هذه الملفات غير موجودة، فقط app/layout.tsx). حماية /seller/* و/driver/* تعتمد على فحوص client-side قابلة للتجاوز (role!=='seller' ثم redirect) مع وميض المحتوى قبل التحويل. صفحة driver/orders تقرأ driverId من query param وتحمّل مباشرة. lib/auth/session.ts يوفّر getCurrentUid/requireUid/requireOwner/getCurrentUser لكن لا requireAdmin/requireRole موحّد، وفحص admin مبعثر inline في orders.ts:448 (caller.role!=='admin'). الدفاع يعتمد كليًا على فحص كل أكشن فرديًا (هشّ وعرضة لأكشن منسي).
- **الإصلاح:** إنشاء requireAdmin()/requireRole() في lib/auth/session.ts (أو lib/auth/admin.ts) تتحقق من session cookie + الدور سيرفر-سايد (يُفضّل عبر custom claim للأدمن). إنشاء middleware.ts على الجذر يقرأ __session وdriver_session ويعيد توجيه غير المخوّل بعيدًا عن /seller و/driver و/admin قبل تسليم الصفحة. إضافة server layouts حارسة لكل مساحة. اشتقاق driverId من الجلسة لا من الرابط. اعتماد دفاع بطبقتين (مسار + أكشن) وتوحيد فحص admin في orders.ts عبر الـhelper.
- **الملفات:** `middleware.ts`، `lib/auth/session.ts`، `lib/auth/admin.ts`، `app/seller/layout.tsx`، `app/driver/layout.tsx`، `lib/actions/orders.ts`، `app/driver/orders/page.tsx`

#### SEC-04 — حماية إجراءات الإشعارات: IDOR في القراءة/التعليم كمقروء والإنشاء التعسّفي
