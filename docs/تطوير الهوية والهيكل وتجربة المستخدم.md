# خطة تطوير الهوية البصرية والهيكل وتجربة المستخدم لمنصة محلك

> **الإصدار:** 1.0 — يونيو 2026 · **النطاق:** السوق المصري (EGP، عربية RTL أولاً، إطلاق مركّز على حيّ واحد)
> **المنهج:** كل توصية في هذه الوثيقة مبنية على دليل من ملف الجمهور المستهدف، وملخّص الوضع الحالي والبحث والمنافسين، وتدقيق فعلي للكود (`app/`, `components/`, `app/globals.css`, `lib/`) — بعد تسويتها مع نقد عدائي متعدد العدسات (الثقافة، الجدوى التقنية، الأعمال، إمكانية الوصول).

## مقدمة وفلسفة التطوير

**محلك** سوق إلكتروني محلي مصري متعدد الأطراف (مشترون / بائعون-أصحاب محلات / سائقون / أدمن) يضم نقاط بيع POS ومحاكي سوبر ماركت 3D. مهمّته رقمنة **محل الحي المصري** بالكامل (متجر + POS + توصيل) في منصّة واحدة بالعربية — لا منافسة أمازون/نون على السلع المعلّبة بالسعر، بل امتلاك **الفجوة** التي لا يملكها أي منافس: بين التوصيل (طلبات/بريدفاست)، ورقمنة التوريد (MaxAB/كرتونة)، وPOS المنعزل (Foodics).

تنطلق هذه الخطة من خمسة مبادئ حاكمة استخلصها التحكيم من الأدلة:

1. **العرض يقود الطلب، والترتيب ملزم.** وثيقة الجمهور ترتّب الشرائح صراحةً: **البائع (1) ← الأدمن (2) ← المشتري (3) ← السائق (4)**. لا قيمة للمشترين بلا كثافة متاجر، والأدمن شرط تمكيني لتوسيع العرض بأمان. أي جهد يُوزَن بخدمته لهذا الترتيب.
2. **الثقة هي العملة، لا التمييز الجمالي.** 41% من المراجعات سلبية، 38% فقط راضون، COD = 34.37% من المدفوعات و65–70% من معاملات السوق. كل قرار يُقاس بأثره على ثقة المشتري الحذر (منى/الحاج سمير) ووضوح البائع محدود المهارة (عم محمود).
3. **أكبر الفجوات المُدِرّة وظيفية لا تجميلية.** لوحة الأدمن الغائبة، رقمنة دفتر الديون، محفظة/تسوية السائق، وإشارات الثقة (COD/الإرجاع/التتبّع) — هذه تسبق صقل الهوية. الهوية تُنفَّذ بإصلاحات رخيصة عالية العائد على الثقة بالتوازي، لا بمشاريع تبتلع جدول الفريق الصغير.
4. **"البنية موجودة" ≠ "مصدر البيانات موجود".** توفّر Leaflet لا يعني بثّ GPS حي؛ توفّر العمولة لا يعني حساب مسافة. تُفكَّك كل توصية مركّبة وتُقدَّم نواتها الرخيصة المضمونة أولًا.
5. **إمكانية الوصول والأداء وRTL طبقة عرضية إلزامية.** شبكة وسيطة 24Mbps، أجهزة فئة متوسطة، جمهور يضم كبار سن ومحدودي مهارة. الخفّة نفسها إشارة ثقة وملاءمة سوق.

> **التحقق الكودي المفصلي (مؤكَّد):** لا `app/admin`؛ صفحة السائق الوحيدة `/driver/orders` بترميز نصوص مشوّه (mojibake) وHeader/Footer سطح مكتب؛ `qpos/page.tsx` ملف وحيد بـ8,748 سطرًا؛ `Store3D.tsx` 2,950 سطرًا محمّل lazy؛ نموذج الدور في `auth-context.tsx` محصور بـ`customer|seller` بينما `orders.ts:447` يُنفّذ تحقق `admin` سيرفر-سايد؛ المتجر = مستند مستخدم بدور seller؛ الفئات إيموجي حرفيًا (90 إدخالًا)؛ `globals.css` يعلن `--primary` أزرق (oklch 0.45 0.18 260)؛ خط Cairo **غير محمَّل إطلاقًا** (لا `next/font`، `body` = `antialiased` فقط)؛ `logo.svg` = 59,541 بايت base64؛ `dir` مثبّت يدويًا على "rtl"؛ 778 موضع لون خام عبر 67 ملفًا؛ صفحة طلبات البائع تحميل لمرة واحدة بلا `onSnapshot`؛ لا manifest ولا Service Worker؛ ثغرة ملكية السائق (`markStorePickedUp` تأخذ `driverId` خامًا).

## المحور الأول: الهوية البصرية — النسخة النهائية المتّزنة

### رؤية المحور

**محلك** علامة "سوق الحي المصري الرقمي" — دافئة وموثوقة وحديثة، تترجم قيمتها الجوهرية (القرب + الثقة المحلية + الدفع عند الاستلام) إلى لغة بصرية مملوكة لا تشبه أزرق أمازون ولا قالب shadcn/v0 العام. لون العلامة الأساسي **أخضر مصري هادئ موثوق** (دلالة ثقة/نماء في الثقافة العربية)، مدعومًا بـ**ذهبي/عنبري للقيمة والعروض** على أسطح كريمية دافئة، مع الإبقاء على **الأزرق كـ token دلالي محصور** (معلومة/أمان الدفع/رابط) لا كلون أساسي.

لكن — وهذا تعديل جوهري فرضه النقد العدائي والتدقيق الفعلي للكود — **الهوية البصرية ليست أولوية النمو رقم 1**. وثيقة الجمهور ترتّب البائع (1) فالأدمن (2) كشرطَي نمو، وأكبر الفجوات المُدِرّة (لوحة الأدمن، دفتر الديون، محفظة السائق) وظيفية لا بصرية. لذلك تموضع هذا المحور: **إصلاحات هوية رخيصة عالية العائد على الثقة (اللون، الشارات، الخط، الأداء) تُنفَّذ مرحليًا دون ابتلاع وقت الفريق الصغير، وتأجيل كل ما هو "تمييز مصمّم" لا "حاجة مستخدم"**.

ثلاثة مبادئ حاكمة استخلصناها من التحكيم:
1. **الثقة قبل التمييز:** كل قرار يُقاس بأثره على ثقة المشتري الحذر (منى/الحاج سمير) ووضوح البائع (عم محمود)، لا بتمايز جمالي لا يلمسه الجمهور.
2. **إمكانية الوصول والأداء جزء من الهوية:** تباين AA موثّق بالأرقام، خط محمَّل فعليًا، وخفّة على شبكات 24Mbps — الخفّة نفسها إشارة ثقة.
3. **لا حالة هجينة منشورة:** التحويل مرحلي بترتيب تبعية صارم، وكل مرحلة تُدمج فقط عند اكتمال نطاقها.

### ترتيب التبعية (حاسم — أضافه التحكيم)

النقد أجمع عبر عدسات متعددة على غياب خريطة تسلسل، وأن تنفيذ البنود بالتوازي يُنتج هويات مكسورة. الترتيب الملزم:

> **VIS-05أ (تحميل الخط) ← VIS-01 (تثبيت قيم الألوان + التباين) ← VIS-02 المرحلة 1 (ربط مكوّنات الثقة العالية) ← VIS-07 (الشارات) + VIS-03 (الأيقونات) + VIS-04أ (إصلاح الشعار الهندسي) + VIS-09أ (أداء الصور) ← VIS-02 المرحلة 2 ← (مؤجّل: VIS-05ب خط ثانٍ، VIS-06 داكن، VIS-04ب شعار إبداعي، VIS-09ب تصوير)**

السبب: تغيير الـ tokens (VIS-01) بلا إزالة الـ hex المثبّتة (جزء VIS-02) يُنتج أزرق+أخضر متعايشين — هوية أسوأ من الحالية. والخط غير محمَّل أصلًا، فأي سلّم تايبوغرافي قبل تحميله = لا شيء.

### التوصيات النهائية (مرتّبة بالأولوية)

#### VIS-05أ — تحميل خط Cairo فعليًا (الخطوة صفر) — أولوية: حرجة/عالية جدًا

**ماذا:** تحميل Cairo عبر `next/font/google` (subsets: ['arabic']، الأوزان [400,600,700]) في `layout.tsx` وتطبيق className على `<html>`، أو `@fontsource` للاستضافة الذاتية لتفادي طلب خارجي على شبكات 24Mbps.

**لماذا:** **أخطر إغفال تقني في المحور كله، أكّدته بالكود:** لا `next/font`، لا أي تبعية خط في `package.json`، و`<body className="antialiased">` فقط — التطبيق حاليًا يعرض بخط النظام (system-ui) **وليس Cairo إطلاقًا**. كل حديث عن "تثبيت أوزان Cairo" بلا تحميل = عبث. هذا يضرب كل عنوان ونص أمام كل مستخدم الآن.

**ماذا يتغيّر:** إضافة تبعية الخط + تحميله self-hosted بأوزان ثلاثة فقط (لضبط حِمل الأداء) + ربطه بـ `<html>` لمنع FOUT وتحسين LCP.

**أولوية:** عالية جدًا · **جهد:** صغير · **أثر:** عالٍ

**كيف عالجنا النقد:** هذه النقطة لم تكن في المقترح الأصلي إطلاقًا (افترض أن Cairo "مضبوط")؛ رفعها التدقيق التقني كأولوية حرجة، واعتمدناها كالخطوة صفر قبل أي عمل تايبوغرافي.

#### VIS-01 — لون علامة مملوك: أخضر مصري + ذهبي، والأزرق token دلالي محصور — أولوية: عالية

**ماذا:** تعيين `--primary` أخضر مصري هادئ، و`--accent` ذهبي/عنبري، مع **درجتين للأخضر** (فاتح للأسطح، وداكن L≈0.42-0.45 للنص/الأزرار)، وفصل `--success` (أخضر) عن `--accent` (ذهبي)، والإبقاء على `--info`/أزرق محصور لحالة المعلومة/أمان الدفع.

**لماذا:** `globals.css` يعلن `--primary: oklch(0.45 0.18 260)` أزرق (مؤكَّد سطر 13) يضع محلك في ظل أمازون. المنافسون احتكروا ألوانهم. الأخضر له دلالة ثقة عربية، لكن النقد كشف ثلاث مخاطر عالجناها.

**ماذا يتغيّر:** سلّم درجات كامل للأخضر (50-900) والذهبي كـ tokens، **مع توثيق نسبة تباين AA رقمية لكل زوج لون/خلفية** قبل الاعتماد.

**أولوية:** عالية · **جهد:** صغير (تغيير قيم tokens) · **أثر:** عالٍ

**كيف عالجنا النقد:**
- **"إلغاء الأزرق نهائيًا متهور" (متكرر عبر 3 عدسات):** تراجعنا — الأزرق يبقى token دلاليًا (info/أمان الدفع/رابط)، لا primary. حذفه كليًا يُضعف إشارات الأمان في شاشات الدفع ويزيل اللون الاصطلاحي للروابط.
- **"أخضر بلا تباين موثّق" (حرجة، تكرّرت 4 مرات):** ألزمنا توثيق رقم AA (≥4.5:1 للنص، ≥3:1 لعناصر UI) لكل درجة. الذهبي عالي اللمعان (oklch 0.78) **يُقصر على الحدود/الخلفيات الخافتة فقط، لا تحت نص يحمل الأسعار** — الأسعار بلون foreground داكن عالي التباين.
- **"الأخضر+الذهبي قريب من كرتونة المصرية":** أضفنا شرط اختبار تمايز محلي فعلي ضد كرتونة (لا أمازون فقط) واختبار التباس بصري بصيدلية/كارفور قبل تثبيت الـ chroma.
- **"تغيير التوكن وحده لا يغيّر الهوية":** ربطناه إجباريًا بـ VIS-02 (المكوّنات تستخدم hex مثبّتة لا تقرأ التوكن).

#### VIS-02 — ربط المكوّنات بالـ tokens وإزالة الألوان الخام (مرحلي) — أولوية: عالية (بعد VIS-01)

**ماذا:** استبدال الألوان الخام والتدرّجات والـ hex المثبّتة بـ tokens العلامة، **على مراحل بترتيب أثر**.

**لماذا:** **التشخيص صحيح والنطاق أكبر بكثير مما قُدّر:** تحقّقتُ فعليًا — **778 موضعًا لألوان خام/تدرّجات عبر 67 ملفًا** (لا 82 عبر 15 كما ادّعى المقترح؛ ولا حتى 426 كما قدّر النقد — أكبر من الجميع). جزء منها hex مثبّتة (`from-[#0f172a]` في BannerCarousel/Header) لا تُلتقط بقاعدة lint بسهولة. qpos وحده 108 مواضع. الفوضى المتسقة الحالية أقل ضررًا للثقة من حالة هجينة نصفها أخضر/نصفها أزرق.

**ماذا يتغيّر:**
- **المرحلة 1 (المسارات عالية الثقة):** ProductCard, StoreCard, Header, Footer, BannerCarousel, checkout, home-client-sections — حيث يحكم المشتري على المصداقية قبل الدفع (≈80% من الأثر).
- **المرحلة 2:** باقي الواجهة.
- **مرحلة أخيرة معزولة:** qpos (نظام معزول وظيفيًا، يراه البائع المُتبنّي لا المُكتسَب الجديد).
- إنشاء **طبقة gradient tokens** (`--gradient-brand`) بدل استبدال يدوي لكل from/to.
- استبدال hex المثبّتة بـ `var()` **قبل** أي قاعدة lint، ثم قاعدة ESLint (no-restricted-syntax) لمنع الانحدار **بعد** التنظيف لا قبله.

**أولوية:** عالية · **جهد:** كبير جدًا/متعدد المراحل (مُصحَّح من "كبير") · **أثر:** عالٍ

**كيف عالجنا النقد:**
- **"تقدير الجهد مبخوس 5-9×" (حرجة، إجماع 4 عدسات):** صحّحنا التصنيف إلى "كبير جدًا/متعدد المراحل" وقسّمناه على مراحل بأولوية أثر مع شرط **"لا حالة هجينة منشورة"**.
- **"قاعدة lint لا تلتقط hex المثبّتة":** أضفنا خطوة استبدال hex بـ var() أولًا، وأجّلنا قاعدة الـ lint لما بعد التنظيف.
- **"خطر انحدار بصري بلا اختبارات":** أضفنا الحاجة للقطات بصرية/مراجعة يدوية لكل مرحلة (المشروع بلا visual regression).

#### VIS-07 — نظام شارات ثقة موحّد (COD نجمًا) — أولوية: عالية (أعلى عائد على التحويل)

**ماذا:** مكوّن Badge موحّد لمجموعة شارات ثقة، **شارة COD الأبرز** (لا واحدة من أربع متساوية)، كل شارة = **أيقونة + نص + لون معًا**.

**لماذا:** **أقوى بند في المحور وأعلى عائد على الإيراد/التحويل** (إجماع كل العدسات على الإبقاء). الثقة هي العملة (41% مراجعات سلبية، 38% فقط راضون)، وCOD = 34.37% من المدفوعات والمواطن الأول للمشتري الحذر. الشارات تقلّل هجر السلة (Baymard).

**ماذا يتغيّر:** Badge variants فوق `components/ui/badge.tsx` الموجود + lucide. شارة COD بأيقونة ولون أخضر عالي التباين بارزة. ربطها ببيانات حقيقية فقط.

**أولوية:** عالية · **جهد:** متوسط (UI) + جزء بيانات/باكند · **أثر:** عالٍ

**كيف عالجنا النقد:**
- **"شارة زائفة تضرّ الثقة عكسيًا":** شرطنا ربط كل شارة ببيانات تحقّق فعلية (verified/COD/freeReturn في Supabase/Firebase — جزء من الجهد بيانات لا UI). الشارات الثابتة دلاليًا (COD/إرجاع) يمكن إطلاقها فورًا.

- **"تكديس 4 شارات يفسد الموبايل ويصغّر أهداف اللمس":** سقف **شارتين على ProductCard في الموبايل** (COD + موثّق)، والباقي على صفحة المنتج، مع حفظ أهداف لمس ≥44px.
- **"COD ليس مساويًا للبقية":** جعلناه النجم البارز لا واحدًا من أربع.

**أولوية:** متوسطة-عالية · **جهد:** كبير (مُصحَّح بسبب 90+ إيموجي + مستهلكين متعددين) · **أثر:** متوسط (مُخفَّض من "عالٍ")

**كيف عالجنا النقد:**
- **"الإيموجي أرخص إدراكيًا لكبار السن/محدودي المهارة" (عمى محوري):** اعتمدنا أيقونات مصمّتة بلون مميّز لكل فئة على محيط ملوّن (لا رمادي موحّد ميت) لحفظ سرعة المسح البصري.

- **"الخريطة بالـ id لا تطابق التوجيه بالاسم العربي":** مفتاحان (id + اسم عربي).
- **"أيقونة svg صامتة تُنقص إمكانية الوصول" (الإيموجي مقروء دلاليًا):** كل أيقونة `aria-hidden` مع اسم الفئة كنص مرئي، وتباين رمز ≥3:1.
- **"الأثر شبه صفري على التبنّي/الإيراد":** خفّضنا الأثر إلى متوسط.

#### VIS-04ب — إعادة التصميم الإبداعي للوردمارك — أولوية: مؤجّلة

#### VIS-05ب — نظام تايبوغرافي عربي (بعد تحميل الخط) — أولوية: متوسطة-عالية

**ماذا:** سلّم أحجام موثّق (display/h1/h2/h3/body/caption) كـ tokens، أوزان 400/600/700 فقط، `letter-spacing:0`، `line-height ~1.7`، منع italic عالميًا، **body الافتراضي ≥16px (يُفضّل 17-18px) لخدمة كبار السن**.

**لماذا:** الإرشادات العربية صحيحة ومدعومة (أفضل الممارسات سطر 443) وتخدم الحاج سمير/عم محمود مباشرة.

**أولوية:** متوسطة-عالية (رُفعت من "متوسطة" لأنها سلامة وصول عربية رخيصة) · **جهد:** صغير-متوسط · **أثر:** متوسط-عالٍ

**كيف عالجنا النقد:**
- **"الخط الثاني هاجس تمييز غربي لا حاجة سوق" (إجماع 3 عدسات):** أسقطناه نهائيًا — الجمهور لا يميّز Cairo من Tajawal، وخط ثانٍ يثقّل شبكات 24Mbps ويعقّد الصيانة مقابل عائد لا يُدرك. التمايز عبر اللون والشارات أرخص وأكثر أثرًا.

#### VIS-08 — توحيد مسافات/راديوس (مدموج في VIS-01/02) — أولوية: متوسطة-منخفضة

**ماذا:** اعتماد وتوثيق سلّم Tailwind 4 القائم (لا إنشاء من الصفر)، تقييد القيم المسموحة، هرمية راديوس بسيطة (حقول/بطاقات/نوافذ)، **وبناؤها على الخصائص المنطقية (inline/block, border-start-end-radius) لسلامة RTL**، وتوحيد مدد/easing الموشن فقط.

**لماذا:** الفوضى مؤكَّدة، لكن في Tailwind 4 السلالم موجودة أصلًا — المشكلة الاستخدام العشوائي، وحلّها تنظيمي/توثيقي.

**ماذا يتغيّر:** يُنفَّذ كأثر جانبي رخيص ضمن جلسة tokens في VIS-01/02، لا كمشروع مستقل.

**أولوية:** متوسطة-منخفضة (مُخفَّضة) · **جهد:** صغير-متوسط (بعد الدمج) · **أثر:** متوسط

**كيف عالجنا النقد:**
- **"مبرّر التمييز عن v0 قلق مصمّم لا مستخدم":** حذفناه، واستبدلناه بمبرّر صيانة/اتساق ملموس.
- **"تداخل مع VIS-02 يسبب تعارض دمج":** دمجناه في نفس طبقة tokens.
- **"الموشن الثقيل يضرّ الأداء وموبايل لمسي":** قصرنا الموشن على توحيد المدد/easing وتغذية راجعة وظيفية فقط (لا حركات دخول زخرفية)، **مع `@media (prefers-reduced-motion: reduce)` إلزاميًا** (شرط وصول أغفله المقترح)، وإدراك أن hover بلا معنى على 72% موبايل.
- **"الخصائص المنطقية غائبة رغم أنها جوهر RTL":** أضفناها كأساس لطبقة الـ tokens.

#### VIS-09أ — أداء الصور (فوري) — أولوية: عالية (مستقلة)

**ماذا:** تطبيق `next/image` بـ sizes/quality/lazy، تحويل WebP/AVIF، أبعاد محجوزة لتفادي CLS، وفحص Core Web Vitals، **مع معالجة حِمل أصول الـ 3D الثقيلة في Store3D** (تأجيل/اختياري).

**لماذا:** الجزء الأعلى عائدًا والوحيد القابل للتنفيذ برمجيًا فورًا — يخدم كل مستخدم على شبكات 24Mbps ويرفع الثقة (الخفّة إشارة ثقة). المشروع بلا Lighthouse حسب تدقيق UX.

**أولوية:** عالية · **جهد:** صغير-متوسط · **أثر:** عالٍ (أداء/وصول)

#### VIS-09ب — معالجة صور UGC + illustration حالات الفراغ — أولوية: متوسطة

**ماذا:** (أ) **illustration خطّي بسيط لحالات الفراغ/الأخطاء/onboarding** بلون العلامة — فوري ورخيص يعالج فجوة UX موثّقة. (ب) **معالجة آلية موحّدة لصور البائعين (UGC):** قص ثابت، إطار/خلفية كريمي تلقائي، WebP/ضغط، حدّ أدنى دقة مرفوض دونه — يرفع اتساق صور البائعين الفعلية.

#### VIS-09ج — دليل تصوير + جلسة احترافية — أولوية: مؤجّلة

**مؤجّلة** حتى توفّر ميزانية وكثافة بائعين.

**كيف عالجنا النقد:**
- **"البند يخلط أداءً يقينيًا بمشروع تصوير مكلف محجوب بميزانية" (إجماع):** فصلناه لثلاثة مسارات بأولويات مختلفة.
- **"95% من الصور يرفعها بائع محدود المهارة، لا ستوك محترف" (واقع UGC المصري):** استبدلنا "دليل تصوير premium" بمعالجة آلية لصور البائعين + قالب رفع بسيط بقص تلقائي، بدل فرض معايير صارمة تصير حاجز تبنّي.
- **"حالات الفراغ لا يجب أن تُحتجز رهينة لجلسة تصوير":** فصلنا illustration كبند مستقل فوري (يكفيه أيقونة + نص + CTA مبدئيًا).

#### VIS-06 — وضع داكن مرتبط بالهوية — أولوية: مُسقَطة (الآن)

**القرار: إسقاط من نطاق الهوية الحالي.**

**لماذا:** **إجماع شبه كامل عبر العدسات على الإسقاط.** تحقّقتُ — الوضع الداكن **غير مطبَّق فعليًا**: `.dark` رمادي محايد (chroma=0) و`--primary` ينقلب أبيض، واستخدام `dark:` محصور في primitives shadcn فقط بلا أي مكوّن ميزة. مع الـ hex المثبّتة (778 موضعًا) لن تستجيب للوضع الداكن أصلًا. إعادة بناء متغيّرات داكنة لميزة ميتة لا يراها أحد = صقل طابق علوي والأساس متصدّع، بينما VIS-02 (الوضع الفاتح الذي يراه 100%) غير محلول. المبرّر الوحيد (Gen-Z) شريحة الأولوية 3، والبائع (أولوية 1) لا يطلب داكنًا.

**البديل عند اللزوم لاحقًا:** إصلاح سطر واحد (قلب `--primary` الداكن من الأبيض إلى أخضر العلامة + أسطح فحمية) — لا مشروع كامل. يُعاد تقييمه فقط بعد VIS-01/02/07 وبعد قياس فعلي لنسبة مستخدمي الداكن.

### معالجة النقاط العمياء المهمة (الهوية)

**1. سياسة الأرقام والعملة (عمى متكرر عبر 3 عدسات):** نعتمد **الأرقام الغربية (0-9) مع EGP** موحَّدة عبر التطبيق (الشائع تجاريًا والأوضح للمتسوّق الحساس للسعر)، عبر `Intl.NumberFormat` بـ locale صحيح، بلا خلط في الشاشة الواحدة. تحقّقتُ: الأرقام غربية فعلًا في الكود لكن استخدام Intl محدود (≈48 موضعًا أغلبه pos/orders) — **التوحيد عبر Intl فجوة عملية أهم من نقاش نوع الرقم**. يُدرَج كبند تنفيذي رخيص ضمن VIS-01/05ب.

**2. بودجت أداء صريح (سوق 24Mbps):** نعتمد سقف أداء: حدّ أقصى لوزن الخطوط (3 أوزان self-hosted)، صور WebP/AVIF lazy، تأجيل Three.js، وقياس LCP/CLS عبر Lighthouse (مفقود حاليًا). الخفّة إشارة ثقة وملاءمة سوق.

**3. إمكانية الوصول لكبار السن/ضعاف البصر:** توثيق تباين AA رقمي للوضع الفاتح (لا الداكن غير المطبَّق)، body ≥16px، أهداف لمس ≥44px عند الشارات وبطاقات الفئات، ARIA على الأيقونات الصامتة، prefers-reduced-motion — طبقة وصول مغفلة كليًا في المقترح الأصلي.

**4. هوية البائع/POS منفصلة (الأولوية 1 للنمو):** نقرّ أن المحور ركّز على واجهة المشتري. qpos يُعزل في مرحلة tokenization أخيرة (نظام منفصل وظيفيًا)، لكن **هوية البائع في /seller/* تدخل المرحلة 1** لأن البائع أولوية النمو رقم 1.

**5. الثقة خارج التطبيق (واتساب/فيسبوك/OG):** نضيف ضمن VIS-04أ/VIS-09أ: صورة مشاركة OG بهوية العلامة، أفاتار مربّع (variant=mark) لواتساب بزنس وPWA — نقاط اللمس الأولى للثقة قبل فتح التطبيق.

**6. حوكمة محتوى البائع (معضلة الهوية الحقيقية):** أقوى اعتراض جدوى — هوية محكمة تتآكل أمام صور بائعين غير متسقة. الجواب في VIS-09ب: معالجة آلية لصور UGC + قالب رفع بقص/إطار تلقائي، لا فرض معايير يدوية.

**7. خطر إزاحة الأولويات (opportunity cost):** نقرّ صراحة أن هذا المحور **لا يسبق** الفجوات المُدِرّة (لوحة الأدمن، دفتر الديون، محفظة السائق). البنود الرخيصة عالية العائد على الثقة (VIS-05أ الخط، VIS-01 اللون، VIS-07 الشارات، VIS-09أ الأداء) تُنفَّذ بالتوازي مع العمل الوظيفي؛ البنود الكبيرة (VIS-02) مرحلية لا تبتلع الجدول؛ والمكلِفة (الشعار الإبداعي، التصوير) مؤجّلة حتى PMF.

**8. القياس وخطة التحقق:** نربط الهوية بمؤشرات الجمهور (القسم 9.2): قبل/بعد لـ checkout completion ونسبة COD وrepeat rate، وحيثما أمكن A/B للون CTA والشارات — لتفادي "جهد كبير بلا مؤشر نجاح".

## المحور الثاني: الهيكل المعلوماتي والأفضلية (Information Architecture)

### رؤية المحور (بعد التسوية)

يتحوّل "محلك" من مجموعة مسارات منفصلة ملتصقة بحلول التفافية إلى **منصّة متعددة الأدوار بهيكل معلوماتي صريح، مبنية على استراتيجية "حيّ واحد مركّز" لا على نمط super-app ناضج**. الناظم الحاكم بعد التسوية ثلاثي: (1) **العرض يقود الطلب** — البائع ثم الأدمن أولًا، (2) **أقل تعقيد ممكن** احترامًا للأمية الرقمية للبائع (عم محمود) والسائق (أحمد)، (3) **التمايز الدفاعي الوحيد = القرب الجغرافي وعلاقة التاجر-الزبون** لا الحجم/السعر.

الفرق الجوهري عن المقترح الأصلي: نتبنّى **نفس البنية الهدف** (sitemap متعدد الأدوار مع أدمن وسائق موسّع) **كاتجاه معماري**، لكن ننفّذها على **مراحل مبوّبة بعتبات كثافة**، ونصحّح تقديرات الجهد المتفائلة منهجيًا، ونغلق ثلاث نقاط عمياء حرجة أغفلها المقترح: **الطبقة المالية (دفتر الديون/المحفظة/شفافية العمولة)**، و**طبقة التفويض والأمان (requireAdmin + Security Rules + ثغرة ملكية السائق القائمة)**، و**سياسة الوصول/RTL/الأرقام العربية**. هذه ليست تفاصيل تجميلية بل شروط تمكينية لنجاح أي إعادة هيكلة.

> **التحقق الكودي:** أُكِّدت كل الادعاءات المفصلية فعليًا — لا يوجد `app/admin` (تحقق بالـGlob)، صفحة السائق الوحيدة `/driver/orders`، `qpos/page.tsx` ملف وحيد بـ8,748 سطرًا (monolith لا "493KB" فقط)، `Store3D.tsx` بـ2,950 سطرًا، نموذج الدور في `auth-context.tsx:28` محصور بـ`"customer" | "seller"` بينما `orders.ts:447` يُنفِّذ `caller.role !== "admin"` سيرفر-سايد، والمتجر = مستند مستخدم بدور seller (`stores.ts:169`: `where("role","==","seller")`)، والفئات إيموجي حرفيًا (`home-client-sections.tsx:61-63`)، و`getStores` خلف `unstable_cache` عالمي بـ`revalidate:120`.

### التوصيات النهائية مرتّبة بالأولوية

رُتِّبت التوصيات بعد التسوية حسب **نسبة العائد/التكلفة + خدمة أولوية النمو** لا حسب الترتيب الأصلي. الترتيب التنفيذي المعتمد: **المكاسب الرخيصة عالية الثقة أولًا (IA-04, IA-08, واتساب من IA-09)، ثم الأساس المعماري الآمن (IA-A الأمان، IA-02 المعدّل)، ثم MVP الأدمن (IA-01)، ثم الباقي مبوّبًا، والسائق الكامل والـ3D آخرًا**.

#### المرتبة 1 — IA-04: إعادة هيكلة الاكتشاف حول "الحي القريب أولًا" (مع fallback إجباري)

- **ماذا:** إعادة تنظيم الصفحة الرئيسية و`/search` و`/category` لتبدأ بـ"متاجر حيّك" المبنية على الموقع، مع فلتر مسافة افتراضي وشارات "قريب منك/توصيل اليوم".
- **لماذا:** هي **التمايز الدفاعي الوحيد** الموثّق في ملف الجمهور (القرب + علاقة التاجر-الزبون)، ودرس المنافسين صريح: لا تنافس أمازون/نون على الحجم/السعر. أجمعت العدسات الأربع على **إبقائها** كأقوى توصية وأعلاها عائدًا مقابل تكلفة، والبنية تدعمها جزئيًا (`latitude/longitude` على المتاجر + Leaflet مستخدم فعلًا).
- **ماذا يتغيّر:** الفرز يبدأ بالقرب؛ القرب يصبح بُعدًا تنظيميًا في IA لا فلترًا ثانويًا.
- **الأولوية:** عالية · **الجهد:** متوسط · **الأثر:** عالٍ.
- **كيف عالجنا النقد:** (1) أضفنا **مسار fallback إجباريًا** (متكرر عبر 3 عدسات): حين تقل كثافة الحي عن عتبة، اعرض "أقرب المتاجر إليك" بنطاق أوسع تدريجيًا + شارة "نوسّع في حيّك قريبًا" بدل شاشة فارغة تكسر الثقة، مع **اختيار حي يدوي** عند رفض/فشل الموقع. (2) **حلّ تخزين مؤقت:** لا نكسر `unstable_cache` العالمي — نُبقي `getStores` مخزّنًا ونطبّق فرز haversine **client-side** (المتاجر قليلة في حي واحد، مقبول حسابيًا)، ونؤجّل geohash/geofirestore حتى يفرضه الحجم. (3) **الموقع اختياري لا بوّابة إجبارية** (تفاديًا لمشكلة إجبار الموقع المسجّلة في checkout). (4) ربطها بعتبة حد أدنى من المتاجر المعتمدة (تبعية على IA-01).

#### المرتبة 2 — IA-08: فئات بأيقونات Lucide + حالات خطأ/فراغ مرئية + سياسة أرقام موحّدة

- **ماذا:** استبدال إيموجي الفئات (🛒💊👕) بأيقونات Lucide موحّدة الوزن بلون العلامة، تثبيت البحث الثنائي (منتجات/متاجر) كنمط معياري، وإضافة حالات فراغ/خطأ مرئية بدل المعالجة الصامتة.
- **لماذا:** الإيموجي يضعف الثقة (العملة الحقيقية، 41% مراجعات سلبية) ويتغيّر شكله بين الأجهزة، وLucide مستخدم في كل الكود فالجهد صغير حقيقي. أجمعت العدسات على **إبقائها** (أفضل نسبة تكلفة/عائد بعد IA-04).
- **ماذا يتغيّر:** اتساق بصري للفئات عبر الصفحة الرئيسية/البحث/الفئة، ورفع التحويل بإنهاء "الظلام" عند فشل الاستعلام.
- **الأولوية:** عالية · **الجهد:** صغير · **الأثر:** متوسط-عالٍ.
- **كيف عالجنا النقد:** (1) **رفعنا "حالات الخطأ/الفراغ المرئية" لتكون البند الأساسي** لا تجميل الأيقونات (قيمة ثقة أعلى — عدسة الوصول). (2) **اقتران الأيقونة باسم الفئة بخط Cairo كبير دائمًا** + `aria-label` نصي عربي والأيقونة `aria-hidden` (الأيقونة الخطية وحدها أقل فهمًا للحاج سمير الأكبر سنًا، وأسوأ لقارئ الشاشة). (3) **سياسة أرقام موحّدة عبر `Intl.NumberFormat` بـlocale واحد** (تحقق فعليًا من خلط `toLocaleString` بلا locale موحّد — خطر أرقام شرقية/غربية على شاشة واحدة). (4) **فصل التبعية:** ننفّذ الأيقونات بفئات ثابتة في الكود الآن، ونؤجّل "إدارة الفئات من الأدمن" حتى تُبنى الواجهة — لا نجعل تحسينًا رخيصًا رهينة مشروع كبير.

#### المرتبة 3 — IA-09 (مُجزّأ): واتساب/رقم ظاهر فورًا + تأجيل نظام التذاكر

- **ماذا:** المكوّن الفوري: إظهار قناة واتساب (`wa.me`) ورقم هاتف قابل للنقر (`tel:`) في Footer وصفحتي المنتج والمتجر قبل الشراء، عبر كل الأدوار. المكوّن المؤجّل: `/support` منظّم يغذّي `/admin/complaints` + مسار تظلّم السائق.
- **لماذا:** الحاج سمير يطلب حرفيًا "رقم أكلّمه"، وأفضل ممارسات MENA تؤكد أن واتساب الظاهر يرفع التحويل والثقة. الدعم سيُدار بشرًا عبر واتساب في مرحلة الحي الواحد (تجاوز الأمية الرقمية).
- **ماذا يتغيّر:** نقطة دعم منخفضة الحاجز فورًا بتكلفة دقائق.
- **الأولوية:** المكوّن الفوري عالية / المنظّم متوسطة · **الجهد:** الفوري ضئيل / المنظّم متوسط · **الأثر:** عالٍ (ثقة/تحويل).
- **كيف عالجنا النقد:** **فصلنا المكوّنين** (متكرر عبر 3 عدسات): واتساب فورًا (عائد ثقة فوري، صفر تبعية)، وتأجيل `/support` المنظّم وتظلّم السائق حتى تُبنى لوحة الأدمن وتظهر كثافة شكاوى تبرّر الأتمتة. زر واتساب نصي+أيقوني بهدف لمس **44px+** و`aria-label` (عدسة الوصول).

#### المرتبة 4 — IA-A (بند جديد مُضاف): طبقة التفويض والأمان قبل أي بناء حوكمة

- **ماذا:** بند تأسيسي **أضفناه ردًّا على نقطة عمياء حرجة متكررة عبر العدسات**: (1) `requireAdmin()`/`requireRole()` في `lib/auth/session.ts`، (2) Firestore Security Rules مصاحبة، (3) **إصلاح ثغرة ملكية السائق القائمة**: `markStorePickedUp`/`getMultiStoreOrdersForDriver` تأخذ `driverId` خامًا من العميل دون تحقق جلسة — أي طرف يعرف الـID يتلاعب بطلبات سائق، (4) **توصيل `is_approved` الميت**: فلترة `getStores` بـ`is_approved==true` كشرط نشر (سطر واحد عالي الأثر — المتاجر تُنشر اليوم بلا اعتماد).
- **لماذا:** بناء `/admin` أو توحيد السائق فوق فراغ أمني يحوّل كل توصية حوكمة إلى سطح هجوم تصعيد صلاحيات. هذا **شرط تمكيني** لـIA-01 وIA-03.
- **ماذا يتغيّر:** أساس أمني يسبق الواجهات.
- **الأولوية:** عالية (حرجة) · **الجهد:** صغير-متوسط · **الأثر:** عالٍ.
- **كيف عالجنا النقد:** هذا البند هو **استجابة مباشرة** للمخاطر المشتركة في عدستي الجدوى التقنية والوصول (غياب طبقة تفويض، الثغرة القائمة، الدالة الميتة).

#### المرتبة 5 — IA-01 (مُقلَّص النطاق، الجهد مُصحَّح): MVP لوحة أدمن

- **ماذا:** **بدء بشاشتين فقط** بدل ست: `/admin/stores` (اعتماد/رفض + رؤية موقع على نفس خريطة Leaflet) و`/admin/complaints` (مرتبط بـIA-09)، **responsive لا سطح-مكتب-فقط**. تأجيل `/admin/categories`, `/admin/users`, `/admin/analytics`, `/admin/orders` كموجة ثانية بعد تجاوز عتبة كثافة الحي.
- **لماذا:** الفجوة مؤكّدة (لا `app/admin`) والأدمن أولوية 2، لكن الباك-إند **جاهز جزئيًا** (`caller.role !== "admin"` مُنفّذ فعلًا في `orders.ts:447`، والمتجر = مستند users فلا حاجة لنموذج بيانات جديد).
- **ماذا يتغيّر:** فتح اكتساب البائعين بأمان عبر اعتماد المتاجر + فحص الموقع.
- **الأولوية:** عالية · **الجهد:** ~~كبير~~ → **متوسط** · **الأثر:** عالٍ.
- **كيف عالجنا النقد:** (1) **صحّحنا الجهد** من "كبير" إلى "متوسط" (الباك-إند جاهز — أربع عدسات). (2) **قلّصنا النطاق** إلى شاشتين (تجنّب over-engineering لمنصة حي واحد). (3) **concierge governance أولًا:** اعتماد يدوي عبر سكربت/Firebase لأول 20-50 متجرًا، وبناء الواجهة فقط حين يصبح الاعتماد اليدوي عنق زجاجة فعليًا (عدسة الأعمال). (4) **responsive** (الأدمن قد يفحص الموقع من الميدان) مع إعادة استخدام مكوّنات `ui/` لا نظام تصميم منفصل (تفادي ازدواج صيانة RTL). (5) **يعتمد على IA-A** (requireAdmin قبل أي صفحة).

#### المرتبة 6 — IA-02 (مُعاد تصميمه جذريًا): فصل بيانات المتجر + مبدّل دور شرطي خفيف

- **ماذا:** بدل "مصفوفة أدوار على نفس المستند"، نتبنّى الحل الأقل خطرًا بنفس الأثر: (1) **فصل بيانات المتجر إلى مجموعة `stores` مستقلة بمفتاح `seller_id`** (هجرة لمرة واحدة)، (2) `users` بدور أساسي + حقل `availableRoles` للتبديل في الواجهة فقط، (3) **توحيد نوع `User` في `auth-context` (محصور بـcustomer|seller) مع `CurrentUser` السيرفري (4 أدوار)**، (4) **حذف ازدواج `/seller/my-orders`** ودمج "طلباتي كمشتري" في مساحة العميل، (5) مبدّل دور **يظهر شرطيًا فقط لمن `roles.length > 1`، داخل قائمة الحساب (drawer) لا كزر دائم في الـHeader**.
- **لماذا:** الفجوة موثّقة (`Header:295` يبدّل آليًا، الدور scalar). لكن المتجر = مستند user بدور seller (`stores.ts:169`)، فمصفوفة الأدوار على نفس المستند **تكسر كل استعلامات المتاجر/المنتجات/الداشبورد + login (`profileRole !== role`) + `store_name_lower`**.
- **ماذا يتغيّر:** نموذج دور موحّد آمن دون كسر الاستعلامات، وإنهاء ازدواج الطلبات.
- **الأولوية:** عالية · **الجهد:** ~~متوسط~~ → **كبير (هجرة بيانات)** · **الأثر:** عالٍ.
- **كيف عالجنا النقد:** (1) **صحّحنا الجهد** إلى "كبير" + هجرة (عدسة تقنية، severity حرجة). (2) **رفضنا مصفوفة الأدوار على نفس المستند** واعتمدنا فصل مجموعة `stores` (يحمي الاستعلامات + يقلّل حجم قراءات users). (3) **مبدّل شرطي خفيف داخل drawer** لا زر دائم بارز (متكرر عبر 3 عدسات: حمل إدراكي على بائع/سائق أحادي الدور + Header مزدحم على موبايل RTL) مع `aria-current`/`aria-label` عربي. (4) **فصلنا السائق عن هذا النموذج** (انظر IA-03). (5) جزء عالي العائد منخفض الكلفة (حذف `my-orders`) يُنفَّذ فورًا.

#### المرتبة 7 — IA-06 (الجهد مُصحَّح، النطاق محصور): دمج qPOS كوضع بيع سريع

- **ماذا:** زر "بيع سريع" دائم في لوحة البائع يفتح وضع الكاشير عبر `dynamic import` (المسار يبقى للتوافق)، متصل بنفس مخزون `/seller/products`، مع **lazy-load** للحزمة الثقيلة حمايةً لشبكة 24Mbps.
- **لماذا:** البائع أولوية 1 وqPOS أداة الالتصاق اليومية (أغلب بيع الدكان داخل المحل نقدًا)، ويخدم JTBD "ساعدني أبيع دون فتح صفحات متعددة".
- **ماذا يتغيّر:** الكاشير يصبح وضع تشغيل لا جزيرة، متصلًا بالمخزون.
- **الأولوية:** متوسطة · **الجهد:** ~~متوسط~~ → **كبير** · **الأثر:** متوسط-عالٍ.
- **كيف عالجنا النقد:** (1) **صحّحنا الجهد** إلى "كبير" — تحقق فعليًا أن `qpos/page.tsx` **8,748 سطرًا (monolith)**، فالتأجيل يتطلب code-splitting داخلي لا route-level فقط، والدمج يساوي تفكيكًا تدريجيًا. (2) **حصرنا النطاق:** "توحيد bottom-sheet لكل التطبيق" يصبح **مبدأ تصميم لاحقًا لا شرط إطلاق** (تفادي over-engineering يربك عم محمود — عدستان). (3) **تفكيك تدريجي** (استخراج hooks/مكوّنات) مع إبقاء الصفحة قائمة أثناء التفكيك (تقليل مخاطرة الانحدار على ميزة حسّاسة).

#### المرتبة 8 — IA-05 (مُجزّأ): تنظيف ازدواج الطلبات فورًا + تأجيل "الكيان الموحّد"

- **ماذا:** فورًا: حذف `/seller/my-orders` كصفحة + جعل `/seller/orders` حصرًا لطلبات المتجر الواردة. لاحقًا: "كيان طلب واحد بثلاث عدسات" مع `timeline` كمصدر حقيقة (موجود فعلًا على `MultiOrder`).
- **لماذا:** الازدواج مؤكّد ويربك البائع محدود المهارة. لكن "الكيان الموحّد بالعدسات" إعادة تنظيم عرض لا إعادة بناء بيانات عميقة.
- **ماذا يتغيّر:** طلبات في مكان واحد لكل دور، وضوح حالة موحّد.
- **الأولوية:** متوسطة · **الجهد:** التنظيف صغير / الكيان متوسط · **الأثر:** عالٍ.
- **كيف عالجنا النقد:** (1) **فصلنا التنظيف الرخيص عن إعادة المعمار الباهظة** (عدسة الأعمال) — ننفّذ الحذف الآن، ونؤجّل الكيان الموحّد كدين تقني يُعالَج عند الحاجة. (2) **شرط أمان صريح** (عدسة الوصول): عدسة البائع تُفلتر **سيرفر-سايد** لتُظهر محطة متجره فقط من الطلب متعدد المتاجر (منع تسريب بيانات منافس). (3) يعتمد جزئيًا على فصل الأدوار في IA-02.

#### المرتبة 9 — IA-03 (مُقلَّص جذريًا): السائق — أمان فوري + توسّع مؤجّل خلف عتبة

- **ماذا:** **الإبقاء على دخول PIN السريع كمسار افتراضي** (هو الميزة لا العيب)، مع ربط Firebase في الخلفية للحوكمة (OTP مرة عند التسجيل فقط). البدء فورًا بـ**إثبات تسليم بصورة + زر SOS** فقط. تأجيل `/driver/wallet` (نظام مالي) و`/driver/profile` خلف عتبة حجم طلبات.
- **لماذا:** السائق **أولوية 4 (الأدنى)** صراحةً، وملف الجمهور يقول "يمكن البدء بمندوبي المتاجر المباشرين" (سعيد يخدم متجرًا واحدًا ويسوّي يدويًا). إثبات التسليم وSOS أعلى ألم سلامة/نزاع.
- **ماذا يتغيّر:** حماية فورية من النزاعات دون بناء أسطول كامل.
- **الأولوية:** منخفضة-متوسطة · **الجهد:** ~~كبير~~ → **صغير-متوسط (المرحلة الأولى)** · **الأثر:** متوسط.
- **كيف عالجنا النقد:** (1) **قلبنا الافتراض:** PIN السريع ميزة للسائق محدود المهارة على شبكة 24Mbps لا عيب (متكرر عبر 3 عدسات، severity حرجة) — OTP+Firebase الثقيل لكل جلسة يضرب أهم احتياج. (2) **فصلنا الأمان عن التوحيد:** إصلاح ثغرة ملكية السائق فورًا (ضمن IA-A) **بغض النظر عن نظام الدخول**. (3) **أسقطنا المحفظة/التسوية/الصرف الرقمي مؤقتًا** — يفتحان مسؤولية مالية/تنظيمية (حيازة أموال الغير، امتثال البنك المركزي) لا يحتملها فريق صغير غير مرخّص؛ بديلها سجل تحصيل + تسوية يدوية كما يفعل سعيد. (4) **عتبة تفعيل:** لا تُوسّع مساحة السائق قبل كثافة طلبات تبرّرها (تفادي بناء لوجستيات قبل الطلب). (5) أهداف لمس 44px+ وتباين عالٍ (استخدام في الشمس/الحركة).

#### المرتبة 10 — IA-07 (مؤجَّل/مجمَّد): محاكي 3D

- **ماذا:** **عدم حقن 3D في صفحة المتجر**. الإبقاء عليه مسارًا منفصلًا (`route-level code splitting` مضمون، وهو الوضع الحالي الأأمن) يُستدعى بزر صريح مع بوّابة تأكيد "قد يستهلك بيانات". **تجميده كميزة هامشية** خارج IA الأساسي، وإعادة تقييمه فقط بعد إثبات الإيراد والكثافة.
- **لماذا:** الجمهور المحوري (عم محمود، منى، الحاج سمير) لا يطلبه؛ المستفيد الوحيد كريم (Gen-Z، أولوية أدنى). Three.js ثقيل (`Store3D.tsx` 2,950 سطرًا) على الفئة المتوسطة وشبكة 24Mbps، وربط ShelfManager بالجولة عبء صيانة دائم لا يخدم العمولة ولا الكثافة.
- **ماذا يتغيّر:** لا استثمار هندسي نشط الآن.
- **الأولوية:** الأدنى · **الجهد:** —(مجمّد) · **الأثر:** منخفض.
- **كيف عالجنا النقد:** **خفّضناه من "نقل/دمج بأولوية متوسطة" إلى تجميد** (عدسة الأعمال أسقطته، وعدسة الوصول حذّرت أن حقنه في صفحة المتجر عالية التردد يثقل أهم صفحة تجارية حتى لو كان الزر اختياريًا). تحقق فعليًا أنه معزول في ملف واحد محمّل lazy — وهذا أأمن للأداء من حقنه. "بديل 2D افتراضي" المذكور **غير موجود في الكود** (بند بناء جديد يجب تقديره، نؤجّله). كل ساعة هندسية عليه الآن هي ساعة لا تُصرف على اعتماد البائعين أو القرب.

### معالجة النقاط العمياء المهمة (الهيكل)

أغفل المقترح الأصلي نقاطًا عمياء أجمعت عليها العدسات وتمسّ جوهر التبنّي والإيراد. نعالجها هنا كـ**بنود هيكلية مستقبلية مطلوبة في الـsitemap** لا كتفاصيل لاحقة:

1. **الطبقة المالية = محرّك الالتصاق الأكبر المغفل (أخطر نقطة عمياء، متكررة عبر 3 عدسات).** كل دروس المنافسين (MaxAB/Cartona/Foodics/Breadfast/خزنة) تجمع أن التمويل/المحفظة هو أقوى عامل التصاق وإيراد. **نضيف للـsitemap الهدف ثلاثة بنود مستقبلية بأولوية عالية للبائع:** (أ) **رقمنة دفتر الديون/الأجل** — "أكبر وجع نقدي بلا حل" وثلث الدكاكين تبيع بالأجل؛ هذه **أعلى ميزة جذب للبائع أولوية 1، أقوى من 3D ومبدّل الأدوار** ويجب أن تسبقهما في خارطة الطريق الفعلية. (ب) `/seller/wallet` ومحفظة التاجر. (ج) **شفافية العمولة/الاشتراك** قبل تسجيل البائع (معلومة ثقة حاسمة للبائع "حساس مفرطًا للعمولة" — لا مكان لها في الـsitemap الأصلي إطلاقًا). *ملاحظة: التنفيذ خارج نطاق IA المباشر لكن البنية يجب أن تحجز لها مكانًا الآن.*

2. **تكامل واتساب/فيسبوك كقناة بيع.** نورا وعم محمود يبيعان فعلًا عبرهما (Facebook Shops ~65% من التجارة الاجتماعية). السوق لن يهجر قناته. **نضيف نقطة دخول مستقبلية لاستيراد/مزامنة الكتالوج من السوشيال** كشرط تبنّي عملي للبائع.

3. **محور القيمة/السعر مفقود بجانب محور القرب.** منى والحاج سمير حسّاسان جدًا للسعر بسبب تعويم الجنيه. **نضيف "العروض/الأرخص في حيّك" كمحور تنظيمي موازٍ للقرب** في IA-04 (شارة + فرز).

4. **التوريد B2B (الربط بالموردين/MaxAB/Cartona).** أقرب فلسفيًا لنموذج محلك وأقوى عامل التصاق في سوق المحلات. **نحجز له موقعًا مستقبليًا في مساحة البائع** كفرصة شراكة/إيراد.

5. **مسار شراء منخفض الاحتكاك (ضيف).** Baymard: 19% يهجرون السلة بسبب إجبار الحساب. المصادقة الموحّدة بالـOTP لكل الأدوار تتجاهل المشتري الحذر الجديد (الحاج سمير) + **كلفة OTP التشغيلية** على شبكة ضعيفة (خاصة السائق). **نوصي بمسار تصفّح/شراء منخفض الاحتكاك للمشتري الجديد** قبل فرض إنشاء حساب.

6. **طبقة الوصول (a11y) وRTL المنطقي غائبتان كليًا.** تحقق فعليًا أن ARIA شبه معدومة. كل بنود IA تضيف عناصر تفاعلية جديدة. **نفرض كمعيار إلزامي عبر كل المسارات الجديدة:** `aria-label`/`aria-current` عربي، هدف لمس 44px+، تباين 4.5:1، خصائص RTL منطقية (`ms-/me-` لا `ml-/mr-`)، وskeleton loaders (غائبة تمامًا). الجداول الكثيفة في الأدمن أعلى مواضع كسر المحاذاة RTL.

7. **بوّابات الكثافة (sequencing).** **لا تُفعّل مساحة قبل عتبتها:** "متاجر حيّك" بعد N متجرًا معتمدًا، مساحة السائق الموسّعة بعد M طلبًا/يوم. بناء كل المساحات دفعة واحدة في حي واحد هو **السبب الأول لموت الأسواق الناشئة** (متكرر عبر العدسات).

8. **ازدواج Firebase/Supabase وSecurity Rules.** الكود فايربيز-أولًا فعليًا (Admin SDK + Firestore في كل actions) وSupabase غير محسوم الدور. أي توسّع هيكلي يجب أن **يحسم أين تعيش البيانات** ويصاحَب بـSecurity Rules (مدمج في IA-A).

## المحور الثالث: تجربة المستخدم المثلى — النسخة النهائية المتّزنة

### رؤية المحور

تجربة "محلك" المثلى هي **تجربة محل الحي الرقمية**: موبايل-أولاً صارمة على شبكة وسيطة (24Mbps) وأجهزة فئة متوسطة، عربية RTL نظيفة، تجعل **الثقة + الدفع عند الاستلام (COD)** نجمَي رحلة المشتري لا تفصيلًا ثانويًا. لكنها — تصحيحًا لانحياز المقترح الأصلي — تحترم **أولوية الشرائح المعلنة في ملف الجمهور (البائع 1، الأدمن 2، المشتري 3، السائق 4)**: تُقدَّم الميزات أحادية الجانب (التي تنتج قيمة بطرف واحد يوم 1) أولًا لكسر مأزق دجاجة-وبيضة في إطلاق مركّز على حي واحد.

أربعة مبادئ تأسيسية تحكم كل توصية بعد التسوية:

1. **إبراز لا إنشاء، وتوحيد لا إعادة بناء:** تدقيق الكود أثبت أن عدة "فجوات" مزعومة موجودة فعلًا (واتساب/الهاتف في `app/product/[id]/page.tsx`، حقول `expiry_date`/`barcode`/`stock` في `app/seller/products/new/page.tsx`، تفكيك التكلفة في `app/checkout/delivery/page.tsx`، البنية المالية `PaymentMethodConfig` في `app/pos/qpos`). الجهد الحقيقي في الإبراز والتوحيد، لا البناء من الصفر.
2. **"البنية موجودة" ≠ "مصدر البيانات موجود":** توفّر Leaflet لا يعني توفّر بثّ GPS حي من السائق (غير موجود إطلاقًا)، وتوفّر العمولة لا يعني توفّر حساب مسافة/وقت. تُفكَّك كل توصية مركّبة وتُقدَّم نواتها الرخيصة المضمونة الدقة أولًا.
3. **اقتصاد الوحدة و COD المنضبط:** COD أقوى عامل ثقة لكنه ليس مجانيًا (رفض استلام 10–15%، تكلفة توصيل مهدورة، رسوم WhatsApp Business API المتكرّرة). كل ميزة ثقة تُوزَن مقابل هامش العمولة الرفيع، و COD يُقرَن بهوية هاتف موثّقة (OTP) لكبح الرفض.
4. **إمكانية الوصول والأرقام و RTL كطبقة عرضية إلزامية:** لمسة 48px، تباين 4.5:1، `aria-live` للرسائل الديناميكية، `prefers-reduced-motion`، `dir="ltr"` للأرقام/الهواتف، وحسم نظام الأرقام (Intl.NumberFormat بأرقام لاتينية مع EGP) قبل أي شاشة سعر.

> **شروط مسبقة يجب حسمها قبل التنفيذ النظيف** (مرفوعة من الأسئلة المفتوحة إلى تبعيات صريحة): نموذج العمولة (يحكم UX-06)، توحيد هوية السائق مع Firebase (يحكم UX-05)، مصدر GPS حي للسائق (يحكم UX-03)، تفعيل المحافظ (يحكم UX-01)، ونظام الأرقام (عابر لكل توصية مالية).

### التوصيات النهائية مرتّبة بالأولوية

#### المرتبة 1 — UX-04: رقمنة دفتر الديون والتحصيل للبائع (Credit Ledger) — **إبقاء**
**الأولوية: عالية جدًا · الجهد: كبير · الأثر: عالٍ**

- **ماذا:** صفحة `/seller/ledger` لإدارة عملاء الأجل: رصيد مستحق لكل عميل، إضافة دين/سداد بنقرة، سجل معاملات، وتذكير واتساب اختياري.
- **لماذا:** أقوى توصية وأصدقها ثقافيًا (أجمعت العدسات الأربع على "إبقاء"). مؤكّدة بالكود (لا أثر لـ ledger/ديون)، وبملف الجمهور (ثلث المحلات تبيع بالأجل، أكبر وجع نقدي للبائع — الشريحة رقم 1). **هي الميزة الوحيدة أحادية الجانب التي تعمل يوم 1 بلا مشتري أو سائق** — فتكسر مأزق دجاجة-وبيضة وتلائم الإطلاق المركّز على حي واحد. معماريًا متّسقة: جداول Supabase معزولة (`customers`/`ledger_entries`) لا تلمس مخطط الطلبات، وتعيد استخدام نمط `wa.me` الموجود.
- **ماذا يتغيّر:** صفحة جديدة بأقل خطوات يشغّلها "الابن"؛ بناء البيانات منذ البداية كنواة طبقة مالية (بوابة BNPL/تمويل تاجر مستقبلي) لا صفحة معزولة؛ عزل الجدول كامل عن منطق الطلبات.
- **كيف عالجنا النقد:**
  - رُفعت للأولوية 1 (كانت ضمن مجموعة "عالية") استجابةً لإجماع العدسات أنها أعلى عائد وأحادية الجانب — تصحيحًا لانحياز المقترح للمشتري.
  - **تذكير الواتساب يصيغه البائع بنفسه** (لطيف، شخصي) لا قالب مطالبة آلي — احترامًا لعلاقة الأجل في الحي (نقد الثقافة).
  - استخدام `wa.me` فقط لا WhatsApp Business API (تجنّب رسوم متكرّرة — نقد الجدوى).
  - أرقام موحّدة عبر `Intl.NumberFormat`، حقول `inputmode=numeric`، وتأكيد/تراجع قبل السداد/الحذف (نقد إمكانية الوصول).

#### المرتبة 2 — UX-01: إبراز COD كشارة طمأنة بصرية مع تثبيت `payment_method` — **تعديل**
**الأولوية: عالية · الجهد: صغير (بعد التقليص) · الأثر: عالٍ**

- **ماذا:** شارة COD بارزة بلون العلامة ("ادفع كاش عند استلام طلبك") في صفحة المنتج وملخص `delivery`، مع تثبيت حقل `payment_method='cod'` في `createOrder`/`createMultiStoreOrder` ومخطط Supabase.
- **لماذا:** فجوة مؤكّدة (`app/checkout/page.tsx` و`delivery/page.tsx` بلا اختيار دفع، الطلب يُنشأ بـ cod ضمنيًا في `lib/actions/orders.ts`). يلائم واقع <10% يملك بطاقة و65–70% COD. أعلى عائد بأقل تعقيد.
- **ماذا يتغيّر:** **حذف نهائي للبطاقات/المحافظ "المعطّلة بصريًا"** — لا UI ميت. قراءة `paymentConfig` للمتجر من نفس مصدر POS الموجود، ولا تُعرض محفظة/InstaPay إلا حين يفعّلها البائع فعلًا. تثبيت العمود في المخطط ليكون التوسّع لاحقًا غير كاسر.
- **كيف عالجنا النقد:**
  - أُسقطت "البدائل المعطّلة بصريًا" (إجماع 3 عدسات: خطأ ثقافي يبثّ "أردنا دفعًا مسبقًا"، دين تقني، وكارثة وصول — العنصر `disabled` يتخطّاه قارئ الشاشة ويهبط تباينه).
  - رُبطت صراحةً بتوحيد إعداد الدفع بين POS وواجهة المشتري (أكبر فرصة UX ضائعة في النقطة العمياء).
  - أُضيف تثبيت `payment_method` في المخطط (نقد الجدوى التقنية: التغيير ليس "صغيرًا" بلا حقل المخطط).
  - **قُرنت بآلية كبح رفض COD**: تأكيد OTP للطلب (موجود) كحد أدنى لحماية اقتصاد السائق/البائع.
  - تُنفَّذ كـ `radiogroup` فعلي بعنصر واحد محدد (لمسة 48px، تباين 4.5:1، الأيقونة زخرفية `aria-hidden`).

#### المرتبة 3 — UX-07: معالجة الأخطاء الصامتة (أولوية مسار الطلب) + حالات فراغ + Skeleton — **إبقاء (مع إعادة ترتيب)**
**الأولوية: عالية · الجهد: متوسط · الأثر: متوسط–عالٍ (مرتفع في مسار COD)**

- **ماذا:** سياسة معالجة أخطاء موحّدة: استبدال كل catch صامت برسالة + إعادة محاولة، حالات فراغ إرشادية (نص + اقتراح + CTA)، ومكوّن Skeleton مشترك (shadcn).
- **لماذا:** مؤكّد حرفيًا بالكود — `app/checkout/delivery/page.tsx:72-73` يبتلع فشل تحميل السائقين صمتًا (الأخطر: يُظهر "لا سائقين" بدل خطأ فيهجر العميل)، و`app/search/page.tsx` نفس النمط، ولا Skeleton في المشروع. على شبكة 24Mbps هذه أساسات ثقة لا تحسينات.
- **ماذا يتغيّر:** **يبدأ بـ catch الصامت في مسار الطلب** (`delivery/page.tsx` fetchData + handleConfirmOrder) لأنه يضرب نجم الرحلة COD مباشرة، ثم `/search`، وأخيرًا Skeleton الصفحات عالية الزيارة فقط (بحث/سلة/طلبات) لا "عبر التطبيق".
- **كيف عالجنا النقد:**
  - أُعيد الترتيب الداخلي ليبدأ بمسار الطلب لا البحث (إجماع: فشل صامت في COD = طلب ضائع وثقة محطّمة).
  - رُفعت من "بند UI" إلى "سياسة معالجة أخطاء موحّدة" عابرة (النمط منهجي لا موضعي).
  - حُصر نطاق Skeleton بالمسارات عالية الأثر التجاري (نقد الجدوى: استثمار يتجاوز عائده في صفحات منخفضة الزيارة)، مع البناء على اصطلاح `loading.tsx` القائم في `app/store`.
  - رسائل الخطأ/الفراغ بـ `role=alert`/`aria-live`، Skeleton بـ `aria-hidden` + نص "جاري التحميل" مخفي بصريًا، واحترام `prefers-reduced-motion` (تجنّب shimmer ثقيل).

#### المرتبة 4 — UX-06: شفافية أجر السائق قبل القبول (العمولة أولًا) — **تعديل**
**الأولوية: عالية · الجهد: صغير (للعمولة) · الأثر: عالٍ**

- **ماذا:** عرض قيمة العمولة بالجنيه + عنوان الاستلام/التسليم بتباين عالٍ على بطاقة كل طلب في `/driver/orders` قبل زر القبول.
- **لماذا:** الحاجز الأول للسائقين "كل التطبيقات تعصرنا" والشفافية شرط تبنّي صريح. مؤكّد أن القيمة محسوبة فعلًا (`getDriverCommission`) لكنها محجوبة عن السائق في `/driver/orders`.
- **ماذا يتغيّر:** **العمولة بالجنيه أولًا** (دقيقة ومتوفّرة)؛ المسافة كتقدير هوائي (haversine) رخيص لا routing مدفوع؛ الوقت كنطاق تقريبي — وكلاهما **مؤجّل حتى توفّر موقع السائق الحي** (تبعية على UX-03 مرحلة ب).
- **كيف عالجنا النقد:**
  - فُكِّكت "العمولة (سهلة) + المسافة/الوقت (صعبة)": لا حساب مسافة ولا موقع سائق في البنية الحالية (إجماع 3 عدسات: تقدير "متوسط" مضلِّل).
  - **رُبط التنفيذ بحسم نموذج العمولة أولًا** (السؤال المفتوح 1): لا يُعرض رقم أجر قبل التأكد أنه تنافسي — الشفافية تنفّر إن كان الرقم ضعيفًا (نقد الجدوى).
  - زر القبول لمسته 48px ومنفصل عن منطقة التمرير لتفادي القبول العرضي، أرقام موحّدة بتباين 4.5:1.

#### المرتبة 5 — UX-05: إثبات التسليم + سجل تسوية نقدي (لا "محفظة" مالية بعد) — **تعديل (تفكيك)**
**الأولوية: عالية · الجهد: متوسط (للنواة) · الأثر: عالٍ**

- **ماذا:** (أ) إثبات تسليم برمز PIN يُمليه العميل (لا صورة) يتضمّن تأكيد قيمة الكاش المحصّل؛ (ب) سجل/مطابقة تحصيل نقدي يومي بسيط بين السائق والمتجر.
- **لماذا:** فجوة مؤكّدة (`/driver/orders` صفحة واحدة بلا محفظة/تسوية/إثبات)، وملف الجمهور (سعيد: مطابقة الكاش يوميًا). التسوية النقدية وجع حقيقي في سوق COD.
- **ماذا يتغيّر:** **تُؤجَّل "المحفظة" المالية (رصيد/صرف فوري)** إلى ما بعد توحيد هوية السائق مع Firebase ووضوح الامتثال — لأن أرصدة مالية فوق هوية Driver ID + PIN منفصلة مخاطرة أمنية/امتثالية على فريق صغير.
- **كيف عالجنا النقد:**
  - فُكِّكت أربع ميزات بتكاليف متباينة (إجماع 3 عدسات): ثلثاها رخيص (تسوية + إثبات) وثلثها (المحفظة) خطر مؤجّل.
  - **إثبات التسليم برمز PIN لا صورة** (نقد الوصول/الجدوى: رفع صورة على 24Mbps بطيء ومكلف بيانات للسائق الذي يحسب كل جنيه).
  - **الإثبات يربط بقيمة الكاش المحصّل** لإغلاق حلقة التسوية (نقد الثقافة: الأهم في COD تأكيد المبلغ لا صورة).
  - تبعية صريحة على توحيد هوية السائق (السؤال المفتوح 3) قبل أي رصيد مالي.

#### المرتبة 6 — UX-02: تقديم التكلفة الإجمالية مبكرًا + سياسة إرجاع على مستوى المنصة/البائع — **تعديل**
**الأولوية: عالية (شق التكلفة) · الجهد: متوسط · الأثر: عالٍ**

- **ماذا:** (أ) سطر "رسوم التوصيل (تُحدّد عند اختيار السائق)" أو نطاق تقديري في صفحة المنتج/السلة؛ (ب) سياسة إرجاع مرئية كرابط/Disclosure نصي على صفحة المنتج وملخص الطلب.
- **لماذا:** تفكيك التكلفة موجود فعلًا في `delivery/page.tsx` لكن **متأخر** (بعد اختيار السائق) — وهو نمط "مفاجأة سعرية" خطير مع حساسية السعر والتضخم (39% هجر بسبب تكاليف مفاجئة).
- **ماذا يتغيّر:** التوصية **"تقديم" لا "إنشاء"**. لا ادعاء "رسوم محسوبة بالموقع" — الرسوم في الكود تعتمد على اختيار السائق (`driverCommission`) لا مسافة، وفرض حساب فوري على صفحة المنتج = حِمل شبكة بلا داعٍ.
- **كيف عالجنا النقد:**
  - صُحِّح ادعاء "غياب التفكيك" (موجود، العيب التأخير) و"رسوم محسوبة بالموقع" (متعذّر هندسيًا).
  - **سياسة الإرجاع: نص عام على مستوى المنصة كحد أدنى** بدل حقل لكل متجر يُترك فارغًا ("لم يُحدَّد بعد" يضرّ الثقة أكثر من غيابه)، مع خيار للبائع لتجاوزه بسياسته — لأن الإرجاع المجاني التزام مالي لا يقدر عليه عم محمود (نقد الجدوى) ويتطلب آلية استرداد لا تُبنى قبل لوحة الأدمن.
  - Disclosure نصي قابل للوصول بلوحة المفاتيح لا modal ثقيل ولا صورة.

#### المرتبة 7 — UX-09: قبول عنوان نصي بديل + تقليل الحقول (حذف "الشراء كضيف") — **تعديل (حرج)**
**الأولوية: متوسطة · الجهد: صغير (للنواة) · الأثر: عالٍ**

- **ماذا:** قبول عنوان نصي يدوي كبديل كامل عن الإحداثيات في `handleContinue` عند رفض مشاركة الموقع، وتقليل حقول checkout للحد الأدنى.
- **لماذا:** `checkout` يفرض الإحداثيات بلا fallback (عيب حقيقي مؤكّد) — من يرفض مشاركة الموقع لمخاوف خصوصية لا يستطيع الشراء إطلاقًا. الإكمال التلقائي من الخريطة موجود جزئيًا فعلًا (reverse geocoding عبر Nominatim).
- **ماذا يتغيّر:** **"الشراء كضيف" مُسقَط نهائيًا لطلبات COD** — يُستبدل بـ"تسجيل خاطف عبر OTP الهاتف" (الهوية الرقمية المصرية، موجودة في الكود).
- **كيف عالجنا النقد:**
  - أُسقط "الشراء كضيف" (إجماع 3 عدسات "حرجة"): تصادم ثقافي/أمني — طلب COD بلا هوية = طلبات وهمية ورفض استلام يضرب اقتصاد السائق/البائع (ضرب جوميا تاريخيًا)؛ ومعماريًا التدفّق كله مبني على `user.id` فالضيف إعادة بناء كبيرة لا "متوسطة".
  - صُحِّح ادعاء "إكمال العنوان غائب" (موجود جزئيًا) — العيب الحقيقي الوحيد هو fallback النصي.
  - رسائل التحقق بـ `aria-live`، حقول العنوان بـ `inputmode`/`autocomplete` مناسبة.

#### المرتبة 8 — UX-10: لوحة تنبيهات نفاد/صلاحية (حذف بنود الحقول الموجودة) — **تعديل**
**الأولوية: متوسطة · الجهد: متوسط (بعد التقليص) · الأثر: متوسط**

- **ماذا:** (أ) إضافة حقل `low_stock_threshold`؛ (ب) لوحة تنبيهات في `/seller/dashboard` تستعلم "قرب الانتهاء" (من `expiry_date` القائم) و"قارب على النفاد" (`stock <= threshold`).
- **لماذا:** ملف الجمهور (انتهاء الصلاحية وإدارة المخزون أكبر وجعَي البائع — الشريحة 1).
- **ماذا يتغيّر:** **حذف "إضافة حقل صلاحية" و"توسعة الباركود"** — كلاهما موجود فعلًا (`expiry_date` و`barcode` في `app/seller/products/new/page.tsx`). الفجوة الضيقة الحقيقية: حقل حد النفاد + اللوحة.
- **كيف عالجنا النقد:**
  - قُلِّص نصف التوصية المبني على فجوة غير موجودة (إجماع: التحقق كشف الحقول قائمة)، وصُحِّح الجهد من "كبير" إلى "متوسط".
  - **يبدأ بتنبيه "قارب على النفاد" (يُحسب آليًا من المخزون، صفر عبء إدخال على البائع)**؛ يُؤجَّل تتبّع الصلاحية (يتطلب إدخالًا يدويًا مكثّفًا لن يفعله البقّال لـ350 صنفًا) ويُستهدف به **الصيدليات أولًا كـ pilot** (د. هبة أكثر رقمنة وتُدخِل الصلاحية أصلًا).
  - التنبيهات شارة لون بسيطة فائقة الوضوح (أحمر/أصفر) على بطاقة المنتج، لا داشبورد تحليلي (الأمية الرقمية للبقّال).
  - أُخِّرت خلف UX-04 (نقد الجدوى: جهد متوسط لأثر متوسط يجب أن يتأخّر).

#### المرتبة 9 — UX-08: إكمال قناة الدعم الموجودة (دُمج، لا توصية مستقلة) — **تعديل (من إسقاط جزئي)**
**الأولوية: منخفضة · الجهد: صغير جدًا · الأثر: متوسط**

- **ماذا:** (أ) إظهار رقم/واتساب المتجر في صفحة "تأكيد الطلب" وملخص delivery (المكان الوحيد غير المغطّى)؛ (ب) معالجة حالة `stores.phone` الفارغة/غير الصالحة.
- **لماذا:** الاتجاه الثقافي صحيح (واتساب قناة الثقة المصرية) لكن **الميزة الأساسية موجودة ومنفّذة**: `handleWhatsApp` + `wa.me` + `tel:` في `app/product/[id]/page.tsx` (مؤكّد) و`app/store/[id]`.
- **ماذا يتغيّر:** **أُعيد تأطيرها من "إضافة قناة" إلى "إكمال وتوحيد"** وأُدمجت ضمن تحسينات الثقة (UX-07) لا توصية كاملة.
- **كيف عالجنا النقد:**
  - عالجنا تصادم الأحكام (عدسة تقنية: "إسقاط"؛ بقية العدسات: "إبقاء بتعديل") بـ**الإبقاء على النواة الصغيرة الفعلية مع الإسقاط كتوصية مستقلة** — لأن الادعاء الأصلي "لا قناة ظاهرة" خاطئ بالكود.
  - **إلزام البائع بإدخال رقم واتساب صالح عند الاعتماد** (فحص الصيغة موجود) — "رقم لا يردّ أسوأ من لا رقم" (نقد الثقافة).
  - **ضبط مخاطرة التحايل على المنصة (disintermediation)**: إبراز القناة بعد تأكيد الطلب (حيث تمّت العمولة)، وجعلها "استفسار" أخفّ بروزًا من زر الشراء على صفحة المنتج — حماية لقاعدة العمولة في الإطلاق المبكر (نقد الجدوى).
  - الرقم بـ `dir="ltr"` داخل RTL، زر بـ `aria-label` وصفي، رابط `wa.me` بسيط بلا SDK.

#### المرتبة 10 — UX-03: إشعارات المراحل أولًا، الخريطة الحية مؤجّلة ومشروطة — **تعديل (حرج)**
**الأولوية: متوسطة (الإشعارات) / مؤجّلة (الخريطة) · الجهد: كبير (صُحِّح) · الأثر: عالٍ**

- **ماذا:** (المرحلة أ، فورية رخيصة) إشعارات داخل-التطبيق + SMS عند انتقال كل مرحلة في الـ timeline + زر "اتصل بالسائق" (هاتفه موجود) + ETA تقديري نصي. (المرحلة ب، مؤجّلة) بثّ موقع السائق على Leaflet.
- **لماذا:** التتبّع الحالي خط زمني نصي (`order-tracking-timeline`)؛ **Leaflet مستخدم فقط في `map-picker.tsx` لاختيار عنوان ثابت — لا خريطة تتبّع**، و**لا مصدر GPS حي من السائق إطلاقًا**.
- **ماذا يتغيّر:** **أُعيد تصنيف الجهد من "متوسط" إلى "كبير"** والخريطة الحية مؤجّلة كمشروع مستقل مشروط بتطبيق/PWA سائق يبثّ GPS + قناة realtime + توحيد هوية السائق.
- **كيف عالجنا النقد:**
  - أعلى إجماع "حرجة" عبر العدسات الأربع على أن "البنية موجودة فالجهد متوسط" مضلِّل جوهريًا — التتبّع الحي مشروع كامل لا طبقة فوق Leaflet.
  - **WhatsApp Business API مُستبدَل بإشعار داخل-التطبيق + SMS** لتجنّب رسوم متكرّرة تأكل العمولة الرفيعة (نقد الجدوى).
  - **مراعاة بيانات/بطارية السائق** (يتحمّل تكاليفه): بثّ كل 20–30 ثانية لا أسرع، fallback "في الطريق" عند انقطاع الشبكة، وتحميل tiles بطلب المستخدم فقط (lazy) — نقطة عمياء صريحة في ملف الجمهور.
  - لا وعد بنقطة حية قبل توفّر مصدرها (السؤال المفتوح 5).

### معالجة النقاط العمياء المهمة (التجربة)

1. **غياب تجربة الأدمن (فجوة حوكمة حرجة، أولوية 2):** أبرز نقطة عمياء عابرة للعدسات. **توصية تأسيسية مضافة:** بناء `/admin` (اعتماد متاجر + تصعيد شكاوى + إدارة فئات) **شرط تمكيني يسبق نصف توصيات الثقة** — وعود الإرجاع/الدعم/الاسترداد في COD بلا آلية خلفية تولّد إحباطًا أعمق من غيابها. سياسة الإرجاع (UX-02) والاسترداد النقدي معلّقة على وجوده.

2. **الانحياز للمشتري ضد أولوية الشرائح:** صُحِّح بإعادة الترتيب — UX-04 (بائع، أحادي الجانب) المرتبة 1، وثلاث من أعلى أربع مراتب الآن للبائع/السائق (الأولويتان 1 و4) لا المشتري، تماشيًا مع "العرض يقود الطلب".

3. **توحيد الدفع بين POS وواجهة المشتري:** أكبر فرصة UX ضائعة — `PaymentMethodConfig` (cod/wallet/instapay) موجود في `app/pos/qpos`. UX-01 الآن يقرأ قرار البائع من نفس المصدر بدل التعامل مع الدفع كأنه غير موجود.

4. **الأمية الرقمية كمحدّد تصميم:** **مبدأ عرضي مضاف** عبر UX-04/05/10/08: حجم خط أكبر، خطوات أقل، نصوص لا أيقونات مجرّدة، لمسة 48px لكبار السن/محدودي المهارة (الحاج سمير، عم محمود).

5. **نظام الأرقام (شرقية/غربية):** رُفع من سؤال مفتوح إلى **قرار مسبق إلزامي**: `Intl.NumberFormat` بأرقام لاتينية مع EGP، موحّد عبر كل شاشة سعر/فاتورة/عمولة/دين، بلا خلط في الشاشة الواحدة.

6. **الوضع غير المتصل/الشبكة المتقطّعة:** **مبدأ مضاف** لمسار COD (أهم من Skeleton): إعادة محاولة وحفظ مسوّدة طلب ليصمد المسار على 24Mbps و30% من الريف بلا نت سريع.

7. **إمكانية الوصول العرضية:** `aria-live` للرسائل الديناميكية، تباين 4.5:1، لمسة 48px، `prefers-reduced-motion`، `dir="ltr"` للأرقام/الهواتف، وإدارة التركيز في radiogroup الدفع وdisclosure الإرجاع — طبقة إلزامية لا اختيارية.

8. **ميزانية الأداء على موبايل ضعيف:** أي قدرة ثقيلة (خريطة حية، كاميرا باركود) **dynamic import عند الطلب فقط** كي لا تثقل صفحات لم تكن تحتاجها (qpos يحمّل 493KB، و3D عبء قائم) — تماشيًا مع "موبايل-أولاً صارمة".

9. **توحيد هوية السائق:** رُبط صراحةً كتبعية حاكمة لـ UX-05/06 (لا سؤال مفتوح فقط) — لا أرصدة مالية ولا شفافية أجر نظيفة فوق Driver ID + PIN منفصل.

## المحور الرابع: تطبيق الموبايل والتجربة عبر الأجهزة

### رؤية المحور (بعد التسوية)

السوق المصري موبايل-أولًا بالكامل تقريبًا (72.48% من قيمة المعاملات عبر الهاتف، 116 مليون اتصال محمول، سرعة نت محمول وسيطة 24 Mbps فقط، أجهزة متوسطة شائعة). الكود الحالي متجاوب لكنه ليس موبايل-أولًا بالمعنى الحقيقي. الرؤية المتّزنة: **رفع موثوقية اللحظات الحرجة أولًا — قبل بناء بنية تحتية ثقيلة.** أكبر وجع موبايل مُحقَّق هو أن **البائع لا يرى الطلب الجديد إلا بإعادة تحميل الصفحة يدويًا** (تحقّقنا: `app/seller/orders/page.tsx` يحمّل عبر `loadOrders` لمرة واحدة في `useEffect` بلا `onSnapshot` ولا `setInterval`؛ التحديث زر يدوي فقط). هذه الفجوة تضرب صميم نموذج العمولة: طلب لا يُرى = طلب ضائع = ثقة مكسورة.

المبادئ التي تحكم هذا المحور بعد النقد:
1. **فصل العلاجات السريعة عن البنية التحتية.** الـ Service Worker (SW) شرط تمكيني لـ Push والكاش الأوفلاين؛ أي توصية تعتمد عليه تُؤجَّل خلفه ولا تُقدَّم كبند مستقل عالي الأولوية. العلاجات الفورية (polling + صوت، WhatsApp، skeletons، إصلاح الترميز) يجب ألا تنتظر PWA.
2. **لا تجعل Web Push القناة الوحيدة لإشعار التاجر.** أجهزة أندرويد المتوسطة المصرية (Xiaomi/Oppo/Transsion) تقتل الخلفية بعدوانية، وiOS Safari لا يدعم Web Push إلا بعد تثبيت PWA يدوي. القناة الموثوقة للتاجر المصري هي WhatsApp/SMS، مع Push كتحسين تدريجي.
3. **احترام ترتيب أولوية الشرائح في وثيقة الجمهور** (بائع 1، أدمن 2، مشتري 3، سائق 4). لا نضخّ جهدًا كبيرًا في طرف السائق (الأدنى أولوية والأكثر هجرًا) قبل سدّ إشعار البائع وقبل لوحة الأدمن الغائبة (فجوة حوكمة حرجة في كلا الملفّين).
4. **لا تُضِف أحمال بطارية/بيانات على أفقر الأطراف** (بث GPS حي دائم، Push دائم، 3D) إلا اختياريًا ومضبوطًا للاقتصاد في البيانات.
5. **صحّح المبرّرات غير الدقيقة:** الـ 3D مؤجّل أصلًا عبر `dynamic import` (تحقّقنا: `app/supermarket/page.tsx` يستخدم `ssr:false` + loading)، و`next/image` وصيغ webp/avif مفعّلة في `next.config.mjs`، وLeaflet مستخدم كمنتقي موقع ثابت فقط لا كبنية تتبّع.

### التوصيات النهائية (مرتّبة بالأولوية)

#### MOB-03 (مُعدَّلة) — موثوقية إشعار البائع بالطلب الجديد: علاج فوري + WhatsApp/SMS كقناة أساس + Web Push كتحسين

- **ماذا:** ضمان أن يرى البائع الطلب الجديد فورًا عبر ثلاث طبقات متدرّجة الموثوقية، لا عبر Web Push وحده.
- **لماذا:** أخطر فجوة موبايل وأكثرها ملاءمة للسوق، أُجمِع عليها النقد عبر العدسات الأربع بدرجة «حرجة». مُحقَّقة في الكود: صفحة طلبات البائع تحميل لمرة واحدة بلا اشتراك حي، والتحديث يدوي. لا أثر لـ FCM في الكود (`messagingSenderId` فقط في الإعداد). الربط بالإيراد مباشر: طلب متأخر = عمولة ضائعة + ثقة عم محمود مكسورة.
- **ماذا يتغيّر:**
  1. **علاج فوري رخيص (الآن):** `onSnapshot`/polling خفيف لصفحة طلبات البائع المفتوحة + تنبيه صوتي وشارة مستمرة طالما الطلب غير مؤكَّد — يسدّ ~60% من الألم بجزء بسيط من الجهد ودون أي SW.

#### MOB-01 (مُعدَّلة — على مرحلتين) — manifest أولًا (خفيف)، ثم Service Worker محافظ كبنية تحتية

- **ماذا:** فصل صريح بين منفعتين مختلفتي الجدوى والمخاطر.
- **لماذا:** مُحقَّق: لا manifest في `public/`، لا SW، لا plugin في `next.config.mjs`. لكن «التثبيت» ليس القيمة الأساسية للجمهور المحدود المهارة (منى/الحاج سمير)؛ القيمة الحقيقية للـ SW أنه **شرط تمكيني** لـ Push (MOB-03) والكاش (MOB-05ب). وتثبيت PWA سلوك متقدّم نادر لدى هذه الشريحة.
- **ماذا يتغيّر:**
  - **المرحلة أ (عالية، جهد صغير، خطر شبه معدوم):** `manifest.webmanifest` (اسم «محلك»، أيقونة مربّعة بلون العلامة، theme_color، `display: standalone`, `lang: ar`, `start_url`) + ربطه في metadata بـ `app/layout.tsx` + أيقونات. **احذف `dir:rtl` من الmanifest** (المعيار لا يستخدمه). أرجئ صقل التثبيت على iOS.
  - **المرحلة ب (متوسطة، مؤجَّلة):** SW عبر **Serwist** (لا next-pwa المهجور غير المختبر مع Next 16/React 19) بسياسة كاش محافظة جدًا: precache للأصول الثابتة فقط (CSS/JS/خطوط/أيقونات)، **استثناء صريح لكل مسارات المصادقة** (`/seller`, `/driver`, `/account`, `/checkout`, `/api`)، ومنع تخزين أي HTML ديناميكي. مع **استراتيجية versioning/skipWaiting** و**kill-switch لإلغاء تسجيل SW عن بُعد**.
- **الأولوية:** المرحلة أ عالية، المرحلة ب متوسطة · **الجهد:** أ صغير، ب متوسط · **الأثر:** أ منخفض-متوسط، ب تمكيني.
- **كيف عالجنا النقد:** فصلنا المرحلتين؛ أعدنا تأطير الهدف من «الأيقونة على الشاشة» إلى «بنية تمكينية + تقليل احتكاك العودة»؛ عالجنا تقاطع SW مع session cookies (commit الأمني e2b57d4) باستثناء مسارات المصادقة؛ أضفنا versioning وkill-switch؛ KPI = نسبة العودة خلال 7 أيام لا عدد التثبيتات.

#### MOB-09 (مُعدَّلة — مع بند حرج مفقود) — إصلاح `dir` الديناميكي + دالة EGP موحّدة، وlogical properties تدريجيًا

- **ماذا:** ثلاثة بنود غير متجانسة فُصلت وأُضيف لها أخطر عطل RTL فعلي.
- **لماذا:** **بند حرج مفقود مُحقَّق:** `dir` مثبّت يدويًا على «rtl» في `lib/language-context.tsx:25,32` و`lib/i18n-provider.tsx:11` — عند التبديل للإنجليزية لا يتحوّل الاتجاه لـ LTR إطلاقًا، ما يُبطل عمليًا أي قيمة لـ CSS logical properties (تبقى start/end يمينًا دائمًا) ويكسر تجربة LTR. كذلك مُحقَّق: لا دالة عملة مركزية؛ الأسعار `toFixed(2)` خام (product-card، pos-bottom-bar) — خلط تنسيقات يربك المشتري الحساس للسعر.
- **ماذا يتغيّر:**
  1. **(حرج، أولًا):** ربط `document.documentElement.dir` ديناميكيًا باللغة في موضع واحد (rtl للعربية، ltr للإنجليزية).
  2. **(عالٍ، صغير):** دالة `formatEGP` موحّدة عبر `Intl.NumberFormat` بأرقام غربية ثابتة، تحلّ محل `toFixed(2)` الخام.
  3. **(متوسط، تدريجي):** تمشيط فئات Tailwind الفيزيائية → المنطقية (`pl/pr→ps/pe`, `left/right→start/end`, `text-left/right→text-start/end`) كـ«تبنٍّ عند اللمس» لا حملة شاملة (لتفادي كسر RTL القائم). Tailwind 4 يوفّر الفئات المنطقية جاهزة — لا حاجة لـ CSS خام.
  - **حُذف** بند 44px كبند مستقل (موجود جزئيًا حسب تدقيق UX) ودُمج كقاعدة utility ضمن MOB-02.
- **الأولوية:** البند 1 حرج، البند 2 عالٍ، البند 3 متوسط · **الجهد:** 1+2 صغير، 3 متوسط · **الأثر:** عالٍ.
- **كيف عالجنا النقد:** أضفنا بند `dir` الحرج المفقود الذي يشترطه أي عمل RTL؛ فصلنا دالة العملة عالية القيمة؛ حوّلنا migration الـ logical properties إلى تدريجي لتجنّب مخاطرة الانحدار؛ صحّحنا أن الأداة هي فئات Tailwind لا CSS خام.

#### MOB-08 (مُعدَّلة — مبرّر مصحَّح) — بوّابة جهاز/شبكة قبل تحميل 3D، لا «جعل 2D افتراضيًا»

- **ماذا:** حماية الأجهزة الضعيفة عبر gating قبل تحميل Three.js، مع إبقاء الكتالوج العادي كـ«المسار 2D» الطبيعي.
- **لماذا:** **مبرّر مصحَّح:** تحقّقنا أن `app/supermarket/page.tsx` يحمّل Store3D عبر `dynamic` بـ `ssr:false` + loading — أي **مؤجَّل أصلًا** ومسار `/supermarket` منفصل لا يُحمَّل على الرئيسية، والاستشهاد بحجم qpos (493KB) ضد 3D غير ذي صلة (qpos كاشير لا علاقته بـ Three.js). الناقص فعلًا: لا بوّابة كشف جهاز قبل تحميل الحزمة الثقيلة. السوبر ماركت 3D ميزة تمييز دفاعية مذكورة صراحةً («يستحيل على أمازون تقليدها») — لا نضحّي بها.
- **ماذا يتغيّر:** زر «تجربة ثلاثية الأبعاد» صريح يسبق تحميل الحزمة (gate قبل dynamic import)؛ كشف `deviceMemory`/`connection.effectiveType` لإخفاء/تحذير على الأجهزة الضعيفة (تلميح فقط — غير مدعوم على iOS، مع خيار صريح للمستخدم)؛ شاشة تحميل برسالة عربية سليمة وبديل ثابت.
- **الأولوية:** متوسطة · **الجهد:** صغير (الـ dynamic import منجَز؛ لا بناء عرض 2D كامل) · **الأثر:** متوسط.
- **كيف عالجنا النقد:** حذفنا ادعاء «يُحمَّل دائمًا» والاستشهاد المضلِّل بـ qpos؛ أعدنا التأطير حول البوّابة لا بناء 2D بديل؛ راعينا عدم دعم deviceMemory على iOS.

#### MOB-06 (مُعدَّلة — مؤجَّلة، بديل رخيص أولًا) — اطمئنان COD: ETA + اتصال مباشر، ثم بث حي اختياري لاحقًا

- **ماذا يتغيّر:** **المرحلة الأولى (رخيصة):** ETA تقديري + حالة مرحلية («تم الاستلام/في الطريق») على الـ timeline القائم + **زر اتصال مباشر بالسائق** (نمط الحي المصري الفعلي) — يلتقط ~80% من القيمة بكلفة شبكة/بطارية شبه صفرية. **المرحلة الثانية (لاحقًا):** بث **اختياري** يشغّله السائق («شارك موقعي») بفاصل 15–30 ثانية أثناء «في الطريق» فقط مع إيقاف تلقائي، وتفضيل Firestore RTDB/throttling لكبح تكلفة الكتابات.
- **الأولوية:** منخفضة (تعتمد على MOB-04ب) · **الجهد:** المرحلة الأولى صغير، الثانية كبير · **الأثر:** عالٍ (لـ COD).
- **كيف عالجنا النقد:** صحّحنا مبرّر Leaflet؛ خفّضنا الأولوية وربطناها بتبعيتها؛ قدّمنا بديلًا رخيصًا أولًا؛ جعلنا البث اختياريًا مضبوطًا؛ عالجنا تكلفة Firestore وبطارية السائق صراحةً.

### معالجة النقاط العمياء المهمة (الموبايل)

- **WhatsApp كقناة محورية (أكبر إغفال ثقافي):** رُفِّع من سؤال مفتوح إلى ركيزة في MOB-03 (قناة إشعار التاجر الأساس) وأُضيف كزر دعم/اتصال مباشر في MOB-06 — يلتقط قناة الثقة المصرية الفعلية للتاجر والمشتري.
- **موثوقية Push على أندرويد المصري + قيد iOS:** صار مبدأً حاكمًا (المبدأ 2)؛ Push تحسين تدريجي لا قناة وحيدة، مع توثيق صريح لقتل الخلفية وقيد iOS Safari.
- **بطارية/بيانات السائق (أفقر طرف):** عولج في MOB-06 (بث اختياري، تردد منخفض، إيقاف تلقائي) وMOB-08 (gating الـ 3D)؛ لا أحمال دائمة مفروضة افتراضيًا.
- **الأمية الرقمية مقابل أذونات النظام (تثبيت/إشعار/موقع):** خُفِّض الاعتماد على «التثبيت» كقيمة أساسية (MOB-01)؛ نُقلت شاشات الإذن لما بعد أول طلب/تسجيل لا عند الدخول؛ يُعزَّز بالدعم البشري الذي تذكره الوثيقة.
- **`dir` ثابت يكسر LTR:** أُضيف كبند **حرج** في MOB-09 (شرط لأي عمل RTL).
- **الوصول (a11y):** أُدرج كمتطلب عرضي في MOB-02/MOB-07 (أدوار/تركيز في bottom-sheets، أحجام لمس 44px، تباين لنصوص الشريط السفلي الصغيرة text-[9px/10px]، fallback إدخال يدوي للباركود).
- **إجبار/خصوصية الموقع عند checkout:** نُوِّه كفجوة موبايل صميمة تستحق بندًا في محور الـ checkout (fallback عنوان يدوي دون إجبار مشاركة GPS).
- **أوفلاين الكتابة (POS/طلب):** حُسم السقف صراحةً عند القراءة-فقط (MOB-05ب)؛ الكتابة أوفلاين خارج نطاق الفريق الصغير حاليًا.
- **التبعيات المخفية وتكلفة السحابة:** أُعلِن تسلسل التنفيذ (MOB-03 Push وMOB-05ب وMOB-06 تعتمد على SW؛ MOB-06 يعتمد على MOB-04ب)؛ وعولجت تكلفة Firestore writes ورسائل WhatsApp/SMS مقابل هامش العمولة المنخفض.
- **غياب خيط الإيراد + الطبقة المالية:** MOB-03 (إشعار البائع) هو الخيط الوحيد ذو الربح المباشر؛ نُوِّه أن أقوى عامل التصاق في السوق (محفظة/تمويل تاجر/BNPL) يقع خارج هذا المحور ويجب ربط PWA/POS به في محور مالي مستقل.
- **اختبار فعلي + ميزانية JS:** يُوصى بقياس Core Web Vitals/Lighthouse ومصفوفة أجهزة حقيقية (Android Go / 3G مصري) قبل الالتزام بأي SW/FCM/Leaflet التي ترفع حجم JS على نفس الأجهزة الضعيفة.
- **الخط Cairo وأداء تحميله:** تُدرَس بدائل أخفّ للموبايل (Tajawal) وضبط أوزان محدّدة ضمن عمل الهوية/الأداء.
- **Supabase غائب عن البنية:** يلزم حسم مصدر الحقيقة (Firebase مقابل Supabase) لـ realtime/Push/التتبّع قبل بناء طبقات معتمدة عليها.

## خارطة طريق مرحلية

> **المبدأ الحاكم:** سوق متعدد الأطراف، والعرض يقود الطلب. الترتيب الزمني يخدم أولًا **كثافة البائعين في حي واحد مركّز** + **الأساس الأمني والحوكمي**، ثم ثقة المشتري، ثم توسّع السائق والميزات المتقدّمة. كل مرحلة تحترم بوّابات الكثافة و«لا حالة هجينة منشورة».

### المرحلة الآن (0–3 أشهر): الأساس الأمني + جذب البائع + إصلاحات الثقة الرخيصة

**الهدف:** تأمين القاعدة، جعل اعتماد البائعين ممكنًا بأمان، وتثبيت أعلى مكاسب الثقة بأقل جهد — لكسر مأزق الدجاجة والبيضة من جانب العرض.

| البند | لماذا الآن |
|---|---|
| IA-A — طبقة التفويض والأمان + ثغرة السائق + is_approved | لا تُبنى أي حوكمة فوق فراغ أمني؛ المتاجر تُنشر بلا اعتماد اليوم |
| IA-01 — MVP لوحة أدمن (شاشتان) + concierge governance يدوي للأوائل | الأدمن أولوية 2 وشرط تمكيني لتوسيع العرض؛ الباك-إند جاهز |
| UX-04 — رقمنة دفتر الديون | أقوى جذب أحادي الجانب للبائع (أولوية 1)، يعمل يوم 1 بلا مشتري |
| MOB-03 (العلاج الفوري + WhatsApp/SMS) — موثوقية إشعار البائع | طلب لا يُرى = عمولة ضائعة؛ يحمي ثقة عم محمود |
| VIS-05أ + VIS-01 + VIS-09أ — الخط + اللون + أداء الصور | إصلاحات هوية رخيصة عالية العائد على الثقة، الخطوة صفر للهوية |
| VIS-07 + UX-01 — شارات الثقة + إبراز COD | أعلى عائد على التحويل؛ COD المواطن الأول |
| MOB-04أ + MOB-09(1,2) — ترميز السائق + dir الديناميكي + formatEGP | أعطال صريحة تدمّر الثقة فورًا؛ شرط لأي عمل RTL/مالي |
| IA-04 + IA-08 — الحي القريب أولًا + فئات Lucide + حالات فراغ | التمايز الدفاعي الوحيد + اتساق بصري + إنهاء الأخطاء الصامتة |
| IA-09(الفوري) + UX-07 + MOB-05أ — واتساب ظاهر + معالجة أخطاء + skeletons | ثقة فورية صفر تبعية + صمود على 24Mbps |
| IA-05 + MOB-07 + MOB-01أ — تنظيف ازدواج الطلبات + الباركود + manifest | تبسيط البائع + إدخال أسرع + أساس PWA خفيف |

### المرحلة التالية (3–6 أشهر): توحيد المعمار + توسيع ثقة المشتري + النواة المالية للسائق

**الهدف:** تنظيف الديون المعمارية التي تحجب التوسّع، ورفع تجربة المشتري بعد توافر كثافة عرض أولية، وحماية السائق من النزاعات دون مسؤولية مالية.

| البند | لماذا الآن |
|---|---|
| IA-02 — فصل بيانات المتجر + مبدّل دور شرطي (هجرة) | يحرّر نموذج الأدوار قبل أي توسّع، لكنه كبير فيتلو الأساس |
| VIS-02 (المرحلة 1) + VIS-08 — ربط مكوّنات الثقة العالية بالـtokens | إزالة الحالة الهجينة بعد تثبيت اللون؛ مسارات الثقة أولًا |
| VIS-03 + VIS-04أ + VIS-05ب — أيقونات الفئات + الشعار + التايبوغرافي | اكتمال طبقة الهوية المرئية بعد الخط واللون |
| UX-02 + UX-09 — التكلفة المبكرة + سياسة الإرجاع + العنوان البديل | معالجة المفاجأة السعرية وإجبار الموقع (أسباب هجر موثّقة) |
| UX-06 + UX-05 — شفافية أجر السائق + إثبات تسليم + تسوية نقدية | بعد حسم نموذج العمولة؛ يحمي السائق دون محفظة مالية |
| UX-03(المرحلة أ) + MOB-06(المرحلة أ) — إشعارات المراحل + ETA + اتصال | اطمئنان COD رخيص بلا بنية تتبّع حي مكلفة |
| IA-06 — دمج qPOS كوضع بيع سريع (تفكيك تدريجي) | التصاق البائع اليومي؛ يحتاج تفكيك monolith الـ8748 سطرًا |
| MOB-02 + MOB-09(3) — شريط تنقّل المشتري + logical properties تدريجيًا | تجربة app-like للمشتري + سلامة RTL تدريجية |
| UX-10 — تنبيهات نفاد (الصيدليات pilot للصلاحية) | وجع مخزون البائع؛ يبدأ بالنفاد الآلي صفر-عبء |
| MOB-01ب — Service Worker محافظ (Serwist) | بنية تمكينية لـ Push والكاش، باستثناء مسارات المصادقة |

### المرحلة لاحقًا (6–12 شهرًا): الميزات المتقدّمة + التوسّع المشروط بالكثافة + الطبقة المالية

**الهدف:** بناء ما يتطلّب كثافة مثبتة أو ميزانية أو حسم مخاطر مالية/تنظيمية — لا يُبنى قبل إثبات PMF في الحي المركّز.

| البند | لماذا لاحقًا (مشروط) |
|---|---|
| IA-03(التوسّع) + MOB-04ب — مساحة سائق كاملة | مشروط بعتبة كثافة طلبات + إصلاح PIN + حسم Firebase Auth |
| MOB-03(Web Push) — إشعار البائع عبر FCM | تحسين تدريجي بعد اكتمال SW؛ ليس قناة وحيدة |
| UX-03(المرحلة ب) + MOB-06(المرحلة ب) — تتبّع سائق حي | مشروط بمصدر GPS + توحيد هوية السائق + ضبط تكلفة الكتابات |
| VIS-02(المرحلة 2 + qpos) — باقي tokenization | بعد استقرار مسارات الثقة |
| MOB-05ب — كاش أوفلاين قراءة-فقط | مشروط بـ SW؛ بلا أسعار/مخزون |
| IA-07 + MOB-08(الصقل) — محاكي 3D | مجمّد؛ يُعاد تقييمه بعد إثبات الإيراد والكثافة (يخدم Gen-Z أولوية 3) |
| **الطبقة المالية (محور مستقل):** محفظة التاجر/السائق، BNPL، شفافية العمولة، تكامل واتساب/فيسبوك، توريد B2B | أقوى عامل التصاق في السوق؛ يتطلّب حسم ترخيص/امتثال البنك المركزي وشراكات (خزنة/MaxAB) |
| VIS-04ب + VIS-06 + VIS-09ج — الشعار الإبداعي + الوضع الداكن + جلسة التصوير | مؤجّلة حتى PMF + ميزانية تصميم + قياس فعلي للحاجة |
